# Звонок 2026-07-23: Мусохранов — Тимошенко (ревью подсчёта статистики по корешкам)

Тема: Ревью ТЗ/кода ветвления подсчёта статистики (корешки vs сделки) для `GetPartnerList` / реестра заявок; решение по сумме по сделкам

## Контекст

Ревью реализации [[SabyBank-Stub-Rewards-Calculation|подсчёта вознаграждений по корешкам]]. Мусохранов смотрит код и ТЗ параллельно, проходит по алгоритму «Получить список заявок партнёра по реферальной программе». Метод уже вызывается из JSS-консоли — Тимошенко добавил его в ЮАКС (ACL) и проставил уровень доступа `internet-application`.

---

## Что подтвердили

- **`GetPartnerList`** возвращает список партнёров со статистикой (количество) и вознаграждениями **строго в контексте реферальной программы** — `ReferralProgramId` обязательное поле. В отличие от `GetPartners` (партнёры на странице), где реф. программа **не обязательна** — партнёры по всем реф. программам сразу.
- **Ветвление механики подсчёта**: считаем из корешков (`ВидЦеныДокумент` с `ТипСвязи IS NOT NULL`), **если** программа SabyBank **или** включена фича. Формула Тимошенко: *«для SabyBank всегда, а под фичей — и для старых»*.
- Алгоритм выборки корешков: определить бизнес (`@Лицо`) → найти связанные карты → оставить карту, связанную с `ВидЦены`-реф.программой → отобрать `ВидЦеныДокумент`, связанные с этой картой → сортировка по дате создания. Совпадает с реализованным.
- Статусы `ТипСвязи`: **10** = в работе, **15** = успех, **20** = не успех. Для позитивных — по `EffectiveDate` (дата закрытия); для всех — по `ДатаВремя`.

## Флажки в ТЗ (замечание, не блокер)

Мусохранов не понял «флажки», декларированные в начале ТЗ и не используемые ниже в алгоритмике. Тимошенко: это переменные, которые понадобятся в реализации. Вывод: упоминание в ТЗ без использования сбивает — но оставили как есть.

## Новое решение — сумма по сделкам в корешках

Полностью в [[ReferralStub-DealSum-Field]]. Кратко: у `GetPartnerList` есть колонка «сумма по сделкам», а корешок несёт **только статус и вознаграждение**. Решено считать сумму `SUM`-агрегатом по полю «Сумма» `ВидЦеныДокумент` в том же подзапросе, где уже бежим по отобранным `ВидЦены` для `COUNT`. Пока функционал не реализован → писать **пусто/ноль** (и для SabyBank, и для обычных под фичей), чтобы явно зафиксировать «не сделано». Заполнять позже из платформенного/маркетингового метода.

## Открытые вопросы (помечены «странное»)

Вынесены в [[ReferralStub-Stats-Index-Questions]]:
- Зачем фильтровать по `ТипСвязи` при подсчёте **всех** статусов? Тимошенко: перестраховка. Мусохранов: это влияет на попадание в индекс — «большой момент».
- Покрытие индексами: индекс `(ВидЦены, EffectiveDate)` **без Карты** → не используется при поиске по конкретной карте; индекс только по `Карта` есть; есть «жирный» индекс по `ТипСвязи`. Отложено Тимошенко на уровень реализации.

## Организационное

- Тест индексов/запросов удобно гонять на **большой БД** (недавняя новость о её доступности) — поля `ТипСвязи`/суммы заполняются и на обычных картах, реф. программа не нужна для замера скорости.
- Мусохранов сегодня напишет платформенной команде про маркетинговый метод и перестроение агрегатов; Тимошенко тем временем продолжает работу по переносу (каркас), часть методов ещё не готова — появятся позже. Доброску суммы декомпозировать: сначала ветка SabyBank, затем обычные сделки.
