# ReferralProgram History Migration Feasibility

Нет честного способа мигрировать старую историю офферов при переходе на раздельную историю по реф. сетям — ни переименованием на месте, ни переигрыванием событий. Единственный практичный путь — фильтровать существующий единый поток на чтении, без изменения хранения.

## Контекст задачи

Задача №07012946 ставит проблему: кнопка «История» в реестре офферов `ReferralProgram` открывает историю без фильтра по реф. сети — отдаёт все офферы аккаунта, потому что при записи события сохраняется только ID оффера, а не его реф. сеть. Предложенная в задаче схема: имя объекта истории `ReferralProgram_<UUID бизнес-группы>` (параметризовать статическое имя объекта бизнес-группой/реф.сетью) вместо текущего плоского `ReferralLead` (`program_history.py:26`, класс `ReferralProgramHistory` в `loyaltyreferral/referralprogram/referralprogram/program_history.py`).

Часть той же задачи (отдельная история корешков, `ReferralStub_<ID>` через `for_program()` в `stub_history.py`) уже реализована — миграция там не нужна, потому что истории корешков раньше не существовало вообще (см. [[ReferralStub-History-Scope-Cut]]). Вопрос миграции стоит только для **истории самого оффера**, которая копится годами под единым `ReferralLead`.

## Почему офферо-сетевая принадлежность не жёсткая (не блокер, но нюанс)

[[ReferralProgram-Data-Model]]: в `ВидЦены` нет поля «БизнесГруппа» — принадлежность идёт через иерархию `Раздел`. Подтверждён реальный прецедент (задача 06096778) переноса оффера между реф. сетями на бою — меняется `ВидЦены.Раздел`. Это делает связь оффер→сеть мутабельной, но перенос — редкая ручная админ-операция (вызывается из консоли разработчиком), не бизнес-сценарий пользователя. Поэтому мутабельность сама по себе не блокер миграции — влияет максимум на единичные офферы. Настоящие блокеры — ниже.

## Блокер 1 — переименование записей на месте невозможно

Сервис «История» — платформенный BL-объект `History`, реализован не в price-formation, а в `sbis/core` (`History.orx`, offline-прокси) и `sbis/middleware` (`History Router`, `History Storage`), владелец — команда Польс Н.С. Полный публичный API:

- **Чтение**: `List`, `GetClientHistory`, `Actions_By_Objects(_Detailed)`, `GetObjectNameById`, `GetObjectsName`, `GetInstancesDates`, `Last_Changed`, `ExportSpecialEvents`.
- **Запись**: `HandleHistory`, `HandlePackage`, `HandleFile`, `HandleFolder`, `HistoryMsgSet`.

Методов вида Update/Rename/BulkUpdate/Migrate нет ни в одном orx ни одного репозитория, до которых достаёт кросс-репо поиск. Комментарий к прокси `History.HistoryMsgSet` в `sbis/core` прямо называет его точкой входа только для записи новых событий. Поиск прецедентов подобной миграции («разделить общую историю на несколько объектов задним числом») для ЛЮБЫХ других продуктов SBIS дал 0 совпадений — этот кейс никто прежде через публичный API не решал. Сервис ведёт себя как append-only аудит-лог.

## Блокер 2 — переигрывание (read + re-write) не эквивалентно миграции

Технически прочитать историю можно — в самом price-formation уже есть прецедент чтения через `sbis.История.History_Of_Object(None, {'Объект': [...], 'is_configuration': True, 'check_site': False}, None, navigation)` (`importpromocode/history.py:75`, `importdiscountcard/history.py:74`). Возвращает записи с полями `guid`, `_real_time`, `Attributes`.

Но формат записи (`EVENT_FORMAT` в `priceformationcommon/core/history_object.py:78`: `Сообщение`/`Действие`/`Объект`/`ИдО` или `GUID`/`Атрибуты`) не содержит ни поля даты/времени, ни поля автора — `_real_time` при чтении вычисляется сервисом сам и не может быть передан обратно при записи. Если переиграть старые события `HistoryMsgSet`-ом под новым именем объекта:

1. **Дата события станет датой запуска миграции**, а не исходной датой изменения — вся хронология ломается, что фатально для фичи, чей смысл — «когда что поменялось».
2. **Автор** — платформа не хранит отдельное поле «кто изменил»; там, где это важно, его пишут вручную в `Атрибуты` из `sbis.User.GetCurrentUserInfo()` в момент вызова (пример: `importpromocode/history.py:49`). При переигрывании туда попадёт технический аккаунт скрипта миграции, а не реальный автор.
3. **Дублирование** — удалить/переместить старые записи из-под `ReferralLead` нечем (нет такого API), значит один и тот же оффер будет виден в обоих объектах истории с разными (причём неверными у копии) датами.

Итог: переигрывание — не миграция, а фабрикация фейковой истории с искажёнными датами/авторством. Хуже, чем просто не трогать старые записи.

## Рабочий вариант — фильтрация на чтении, без изменения хранения

Не менять схему хранения (не вводить `ReferralProgram_<UUID бизнес-группы>` как объект истории вообще), а на чтении фильтровать существующий единый поток `ReferralLead` по списку ID офферов текущей реф. сети — списку, вычисляемому на лету через `Раздел → БизнесГруппа` (та же логика, что уже используется в `get_list.py`/`get_stats_helpers.py` для фильтрации по сети). Технически — через `История.History_Of_Object` с фильтром по `ИдО`/списку ID, либо через свой БЛ-метод как источник данных для окна истории (второй вариант, который сама задача 07012946 и называет как «более правильный», но не требующий смены имени объекта — только фильтрации). Работает одинаково для старых и новых записей, не требует миграции, не искажает даты/авторов.

Ограничение того же порядка, что и у любого другого варианта: фильтр всегда по **текущей** принадлежности оффера к сети, не по исторической на момент события — но это касается только редких перенесённых офферов (см. выше) и не хуже, чем у альтернатив.

## Итоговый вывод

| Вариант | Возможен? | Причина |
|---|---|---|
| Переименовать `Объект` у старых записей | Нет | У сервиса История нет публичного API правки существующих событий (подтверждено кросс-репо поиском) |
| Прочитать и переписать события под новым именем | Технически да, но это не миграция | Нет полей даты/автора на запись → искажает хронологию и авторство, плюс дублирование |
| Фильтровать существующий поток на чтении по списку ID офферов сети | Да | Не трогает хранение, работает и для старых, и для новых записей |
