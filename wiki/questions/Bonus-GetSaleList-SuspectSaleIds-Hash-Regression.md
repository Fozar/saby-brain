# Bonus.GetSaleList — 13 секунд в `SuspectSaleIds`

Задача №06244326 (`019ef8af-634f-7846-804b-1c14b6edd779`), регламент «Ошибка на стенде», автор [[Скляров-Алексей]]. Стенд `test-online`, аккаунт `лояльность_автотест`, страница «Бонусы/Покупки».

## Симптом и ложные следы

Реестр отрисовывает только первые 30 записей, дальше скролл не подгружает. С этапа «Выполнение» пришла версия фронта: дефолтный `iterativeLoadTimeout` = 10 с, БЛ в него не укладывается, список рвёт запросы → поднять таймаут до 30 с.

Вопрос [[Ютман-Элина|Ютман Элины]] (2026-07-27): почему `Bonus.GetSaleList` работает по 16–17 с, это противоречит концепции [[CursorNavigation-Mechanism|итеративной загрузки]], а на бою метод «довольно бодро» отрабатывает.

Три версии, которые замер отверг:

1. **Размер блока / EMA.** `_iterative_block_size` действительно упёрся в потолок `_MAX_BLOCK = 20_000`, а `Bonus.GetSaleList.IterativeRatioEMA` = 666.67 (20 000 просканированных на 30 результатов). Но выборка самого блока стоит **32.8 мс** — схема EMA ни при чём, снижать потолок бессмысленно.
2. **Отсутствие индексов.** Все нужные индексы есть и выбираются планировщиком. По `Документ` их четыре (`Warehouse`, `Warehouse_Old`, `PriceListDoc`, `AutoGeneratedIndexDokument` — `PriceFormation.Online.dicx:1016-1150`), по `Sale` — `Retail (Sale, ДатаВремя)`. Осторожно: в `PricingRetailOnline.dicx` объявление `ВидЦеныДокумент` **неполное**, полный набор индексов — в `PriceFormation.Online.dicx:762-1179`.
3. **Доработка только в 26.4100.** Опровергнуто git: `Suspect*` введены коммитом `54aa5a299c` (2026-06-08, задача `019e9bc5`), первый rc — `rc-26.3211`. В `rc-26.3248` (бой на момент разбора) текст обоих CTE **побайтово совпадает** с 26.4100 и 26.5100, `_MAX_BLOCK` тот же.

## Root Cause

`EXPLAIN (ANALYZE, BUFFERS)` основного запроса `BonusSaleListIterative`:

| Узел | Время | Результат |
|---|---|---|
| `UnfilteredRecords` (Index Scan по `EffectiveDate`, 20 000 строк) | 32.8 мс | 11.7k buffers |
| `SuspectWarehouseDocs` | 7.3 мс | rows=0 |
| **`SuspectSaleIds`** | **13 287 мс** | **rows=0** |
| агрегация, `Counts`, `ControlRecord`, сортировки | ~25 мс | |
| **итого** | **13 325 мс** | 31 строка |

99.7% времени — в `SuspectSaleIds`, который возвращает пустое множество.

Планировщик разворачивает коррелированный `EXISTS` в **hash semi-join** и строит хеш не по продажам блока (~2.5 тыс.), а по **всей истории бонусов клиента**:

```
Index Scan using "iВидЦеныДокумент-EffectiveDateSale"
    (cost… rows=475) (actual… rows=428779 loops=7)
    Buffers: shared hit=1869610 read=536422
```

7 бонусных `ВидЦены` × 428 779 строк = **3 001 450 строк**, 2.42 млн буферов (536 тыс. с диска), 7.8 с. Далее `HashAggregate` схлопывает их в 2 991 883 уникальных `Sale` (+3.6 с), хеш не влезает в `work_mem` и уходит на диск: `Batches: 16 (originally 1)`, `temp written=8209`. И только потом это соединяется с 19 917 строками блока — совпадений ноль.

Две причины, почему получилось так:

- **Границы подзапроса не привязаны к блоку.** Условие `vcd."EffectiveDate" < (SELECT MIN("EffectiveDate") FROM "UnfilteredRecords") AND vcd."EffectiveDate" >= COALESCE(!PeriodStart, '-INFINITY')` при `PeriodStart = date.min` — это «вся история до курсора».
- **Промашка оценки в 900 раз** — `rows=475` против `rows=428779` фактических на loop. С такой оценкой hash join выглядел дешёвым.

## Масштабирование — почему это не специфика стенда

Стоимость определяется **количеством бонусных движений конкретного клиента**, а не общим объёмом `ВидЦеныДокумент`: хеш строится по строкам, отфильтрованным по `ВидЦены = ANY(бонусные виды цен клиента)` — в плане это 7 значений из клиентского справочника `ВидЦены` (7 из 400). У автотестового аккаунта таких движений ~3 млн.

Отсюда: на бою проблема не отсутствует, а **не выстрелила** — просто не попался клиент с сопоставимой историей. Деградация нелинейная (хеш перестаёт влезать в `work_mem`). `SuspectWarehouseDocs` быстрый только потому, что складских бонусов на этом аккаунте нет — латентно у него ровно та же форма запроса.

## Фикс — реализован и замерен (2026-07-28)

Смысл `SuspectSaleIds` — отбросить продажи, у которых есть бонусные движения старше блока (их посчитает следующая итерация). Достаточно проверить продажи **из блока**, не строя множество всех продаж истории. Планировщику нужно запретить выворачивать это в hash join:

Смысл фикса — проверять продажи **блока**, а не строить множество всех продаж истории:

```sql
"BlockBound" AS (
    SELECT MIN("EffectiveDate") AS "MinDate" FROM "UnfilteredRecords"
),
"BlockSales" AS (
    SELECT DISTINCT ur."Sale" AS "Sale" FROM "UnfilteredRecords" ur
    WHERE ur."Sale" IS NOT NULL
    OFFSET 0
),
"SuspectSaleIds" AS (
    SELECT bs."Sale" FROM "BlockSales" bs
    WHERE EXISTS (
        SELECT 1 FROM "ВидЦеныДокумент" vcd
        JOIN "BonusPriceEntities" bpe ON vcd."ВидЦены" = bpe."@ВидЦены"
        WHERE vcd."Sale" = bs."Sale"
          AND vcd."EffectiveDate" < (SELECT "MinDate" FROM "BlockBound")
          AND ...
    )
)
```

Аналогично `BlockWarehouseDocs` → `SuspectWarehouseDocs`. `BlockBound` вынесен отдельно, чтобы не пересканировать `UnfilteredRecords` в каждом подзапросе (в исходном плане это 4 отдельных скана 20 тыс. строк).

### Почему `OFFSET 0`, а не `AS MATERIALIZED`

**Стенд на PostgreSQL 10.21** (проверено `SELECT version()` на `test-osr-db19/load-ext-4`), а `AS MATERIALIZED` появился только в PG 12 — там это синтаксическая ошибка. `OFFSET 0` — барьер оптимизатора, работающий на всех версиях: на PG 10 CTE материализуются всегда, на PG 12+ `OFFSET 0` не даёт развернуть подзапрос. Косвенный признак старой версии виден прямо в исходном плане: одноразовые `SuspectSaleIds`/`SuspectWarehouseDocs` показаны как `CTE Scan`, тогда как PG 12+ их бы заинлайнил.

### Замер (тот же стенд, те же аргументы)

| | до | после |
|---|---|---|
| Execution time | 14 530 мс (в разборе 13 325) | **225 мс** |
| Buffers | hit 1 867 774 / read 550 028 | hit 69 526 / read 816 |
| Temp | read 12 738, written 12 708 | нет |
| Строк | 31 | 31 |

Узел `SuspectSaleIds`: Hash Join → **Nested Loop Semi Join**, 13 287 мс → **118 мс**, `Index Cond: "Sale" = bs."Sale"` по `iВидЦеныДокумент-Retail`, 11 210 итераций. `SuspectWarehouseDocs` — 6.6 мс по `Warehouse_Old`. Ускорение ~53×, спил хеша на диск исчез.

### Что доказано, а что нет

Тесты `tests/tests_priceformationonline/loyaltyprograms/bonus/get_sale_list.py` — 41 прогон, OK (2 предсуществующих skip), включая `test_8_no_duplicate_when_warehouse_doc_has_two_effective_dates`.

**Прямая проверка эквивалентности на живых данных вырождена**: множества `Suspect*` старого и нового вариантов совпадают, но оба пусты. На аккаунте нет ни одной продажи с бонусными движениями более чем на одну `EffectiveDate` (последние бонусные движения — 30.09.2025), поэтому непустой случай из реальных данных не конструируется — что заодно подтверждает: 13 секунд тратились на заведомо пустое множество.

Эквивалентность опирается на два других основания:
1. Предикат `EXISTS` зависит только от `X` (`Sale`/`Документ`) → `DISTINCT` выносится до фильтра без изменения результата; `OFFSET 0` влияет только на план.
2. `test_8` конструирует ровно недостающий случай для складской ветки. **Симметричного теста для розничной ветки нет** — стоит добавить.

Открыто: правка лежит на неродственной ветке `26.5100/feature/aatimoshenko/04307101`, нужен перенос на bugfix-ветку (rc-26.3248 или rc-26.4100 — не решено). Не закоммичено.

## Как снимался EXPLAIN

Прямого доступа к БД из окружения нет: `psycopg2`/`psycopg` не установлены, а `pip install` не проходит (SSL-инспекция ломает цепочку сертификатов PyPI). Рабочий путь — **датасурсы PyCharm** через `mcp__pycharm__execute_sql_query`.

Два подвоха инструмента:
- Схема не подставляется: параметр `schemaName` на `search_path` не влияет, `current_schema()` остаётся `public`, а отдельный `SET search_path` в multi-statement не применяется. Имена таблиц надо квалифицировать явно — `"_01216129"."ВидЦеныДокумент"`.
- **Вывод обрезается до 10 строк.** Полный план вытягивается постранично: `mcp__pycharm__fetch_query_result(resultSetId, offset=10, 20, …)`, пока не вернётся «No more rows». План на ~170 строк — это 17 вызовов.

## Ревизия предыдущего вывода

Страница [[Bonus-GetSaleList-Duplicate-W-Records-Iterative-Block-Bug]] в разделе «Индексы — проверено безопасно» утверждала, что `EXISTS`-подзапросы отработают точечными lookup'ами и новый индекс не нужен. Замер это опровергает: индексы действительно есть и выбираются, но планировщик не выполняет подзапрос как точечные lookup'ы — он материализует всю историю в хеш. Проверять надо было форму плана, а не наличие индекса.
