# Решение: в ветке истории реф. программы остаётся только история корешков

Задача №07012946 (`guid` 019f1c60-d761-7b2b-95fa-3ab61865088c), ветка `26.4200/feature/aatimoshenko/07012946`, MR !147258.

Постановка [[ReferralProgram-History-UI-Design]] раскладывалась на три пункта работ ([[referral-history-implementation-breakdown-2026-07-29]]). 2026-07-30 объём урезан: **в этой ветке делается только бэкенд-запись истории корешка**. Всё остальное — следующими задачами.

## Что вошло в объём

Отдельная история изменений корешка заявки, независимая от истории оффера. В историю оффера события по корешкам не попадают **вообще** — это жёсткая формулировка решения, а не «пока не попадают».

- `stub_history.py` — `ReferralStubHistory(HistoryObject)`, объект истории `ReferralStub`. Идентификация экземпляра по `OperationId` корешка (`_id_field='RequestUUID'`), название события — номер заявки (`_name_field='RequestNumber'`). Четыре события: `commit_stub_created`, `commit_status_changed`, `commit_price_changed`, `commit_client_name_changed`.
- `ReferralStub` зарегистрирован в `ReferralProgram.hox` (действия «Создание», «Изменение»).
- `create_stub` пишет создание корешка в его историю; запись обёрнута в `try/except` + `WarningMsg` — история некритична, недоступность сервиса истории не должна ломать создание корешка.
- `update_stub` — раньше писал в историю только вознаграждение. Теперь перед `UPDATE` читает состояние корешка (`_SQL_READ_STUB_STATE`) и пишет **только фактические изменения**: статус/комментарий статуса, имя клиента, вознаграждение.
- `set_stub_price` переключён с истории программы на историю каждого корешка; в `RETURNING` вместо `@ВидЦеныДокумент`/`ДатаВремя` теперь `OperationId`/`RequestNumber`.

Побочный эффект в `update_stub`, важный для регресса: проверка «корешок не найден» переехала выше и теперь срабатывает **всегда**, а не только при переданном `Price`. Интеграция, дергающая `UpdateStub` без `Price` по несуществующему корешку, раньше молча проходила — теперь получит `sbis.Warning`.

## Что вынесено за объём и физически удалено из ветки

- **`ReferralProgram.GetHistoryList`** — метод истории программ одной реферальной сети (пункт 3 разбора). Удалён целиком: реализация, `.orx`, права в `.uax`, тесты.
- **Проваливание из истории оффера в историю корешка** (пункт 2 разбора) — `ReferralLeadHistory.commit_new_stub`, событие «Создана заявка \<дата\> №\<номер\>» в истории программы с UUID корешка в `@event_RequestUUID`.
- **Инфраструктура под это проваливание** — параметр `event_attributes` в `HistoryObject._send_to_history` (`priceformationcommon`) и прокидывание `**kwargs` в `PriceEntityHistory._send_to_history` (`priceformationonline`). Оба файла приведены к состоянию `rc-26.4200`, в диффе ветки их больше нет.
- Группировки и сгруппированный по корешкам реестр (опциональная часть постановки, §«Решение» → «Опционально, не решено окончательно») — не начинались.

Механизм проваливания, который был реализован и откачен, стоит помнить: UUID корешка кладётся в атрибуты события с обязательным префиксом `@event_`, иначе сервис истории их не сохраняет; на чтении приходит в поле `Attributes` уже без префикса. Фронт цепляется к нему через `instanceClickCallbacks`. Это рабочее знание для будущей задачи, а не мёртвый код.

## Как это сделано в git

Ветка была запушена тремя коммитами. Выбран **reset + force-push**, а не revert-коммит — ветка личная, чистая история важнее сохранности запушенного:

- `0de9096066` (история корешков) — оставлен, доработан (удаление проваливания вложено в него через `--amend`, т.к. проваливание изначально не должно было в нём быть) → `0813f6d628`;
- `f3aba92d9c`, `1d6d834068` (`GetHistoryList`) — отброшены.

Итог: ветка = один коммит, `+247/−52` по 9 файлам относительно `rc-26.4200`. `git push --force-with-lease`.

## Поведенческий контракт для QA

Что именно порождает событие в истории корешка — это и есть проверяемая часть решения:

| Действие | Событие | Условие записи |
|---|---|---|
| `CreateStub` | «Создана заявка \<дата\> №\<номер\> от клиента \<имя\>» | всегда; без имени клиента — формулировка без «от клиента» |
| `UpdateStub` | «Изменен статус заявки \<дата\> на «\<статус\>»[: \<комментарий\>]» | статус изменился **или** изменился непустой `StatusDescription` |
| `UpdateStub` | «Изменен клиент заявки на «\<имя\>»» | `ClientName` непустой **и** отличается от текущего |
| `UpdateStub` / `SetStubPrice` | «Изменено вознаграждение по заявке: \<сумма\>» | `Price` не `None` **и** отличается от текущего |

Названия статусов `ТипСвязи`: 10 — «в работе», 15 — «успешно завершена», 20 — «не успешно завершена»; значение вне набора выводится числом.

Ключевые негативные проверки: повторный `UpdateStub` с теми же значениями новых событий **не** порождает; `Price` при статусе ≠ 15 → предупреждение «Вознаграждение можно установить только для успешно завершённой заявки» и в историю ничего; `SetStubPrice` пишет отдельное событие **каждому** корешку, корешки со статусом ≠ 15 не обновляются; ошибка сервиса истории не ломает ни одну из трёх бизнес-операций.

Смотреть историю корешка на текущий момент можно только платформенным окном истории по объекту `ReferralStub` с идентификатором = `OperationId` заявки — кнопки в UI (пункт 1 разбора, на [[Лебедева-Наталья]]) и проваливания из карточки оффера в этой ветке нет.

## Обновление 2026-07-31 — MR-ревью и метод for_program

Ревью MR ([[mr-review-stub-history-call-2026-07-30]]) — Тимошенко повторяет объём (см. выше) Мусохранову. 2026-07-31 11:28 Мусохранов задаёт ключевой вопрос: **как в текущем решении показывается история по корешкам только нужной реферальной программы?** Тимошенко отвечает: общей истории по корешкам сейчас нет вообще, только по отдельности (по одному корешку) — что дословно совпадает с формулировкой объёма выше («в этой ветке делается только бэкенд-запись истории корешка»). Мусохранов реагирует «Звони, что то не то» и уводит обсуждение в (не транскрибированный) звонок.

В тот же день, позже (12:44), в отдельном MR-комментарии Тимошенко фиксирует результат: «Добавил метод `for_program` в класс истории корешков. Возвращает объект истории конкретного оффера. Адаптировал всю запись под использование этой механики» (source: [[mr-comment-for-program-method-2026-07-31]]). Синхронно с этим, в исходном треде постановки задачи, Тимошенко уточняет имя платформенного объекта истории — `ReferralStub` (11:29) и, тем же днём в 12:44, `ReferralStub_<ID>` (source: [[referral-history-implementation-breakdown-2026-07-29]] §«Обновление 2026-07-31»).

**Трактовка (не подтверждена источниками напрямую, но согласована по времени и содержанию):** `for_program` — не отмена решения «истории по программе нет», а добавление серверного метода, агрегирующего события истории всех корешков одной реферальной программы (оффера) — то есть программная, а не UI-группировка, которая в исходном объёме была явно исключена («Группировки не начинались»). `ReferralStub_<ID>` вероятно используется именно для этого агрегированного представления (идентификатор программы вместо `OperationId` отдельного корешка), тогда как `ReferralStub` без суффикса остаётся именем объекта для окна истории одного корешка.

> [!gap] Не хватает прямого технического описания
> Ни один из трёх новых источников (`019fb1d0`, `44bd4968`, обновление `019f1c60`) не формулирует эту связь текстом — только совпадение по времени (оба сообщения в 12:44 того же дня) и логическая непротиворечивость с исходным решением. Следующий ингест MR-диффа или ТД должен подтвердить/опровергнуть.
