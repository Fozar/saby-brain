# Корешки по существующим заявкам РКО: метод в аккаунте Тензора + тонкая ВНР

Navigation: [[SabyBank-RKO-Referral]] | [[ReferralStub-Backfill-Service-Method]] | [[Wasaby-Scripts]]

Задача №05256682 («Создать корешки для старых заявок РКО», веха 26.5100). Тот же console-first
порядок, что и на сделках обычных реферальных программ ([[ReferralStub-Backfill-Service-Method]]):
ядро — служебный метод на один банк за вызов, ВНР — перебор. Метод влит 27.08 (`ae6a15f798`),
скрипт ВНР подготовлен 11.09.

---

## Где что исполняется

Заявки на РКО лежат в аккаунтах банков (Альфа, ТБанк), корешки — в аккаунте Тензора, где живут
реферальные программы SabyBank. Поэтому:

- `ReferralProgram.CreateStubsForExistingRequests(ProgramId, Partner, DryRun)` исполняется
  **в аккаунте Тензора** и постранично (`_PAGE_SIZE = 500`) ходит в аккаунт банка через
  `multitenancy.CreateMultitenantEndpointByClientId(ClientId)`;
- `ReferralProgram.GetBankRequests(Cursor, Limit)` исполняется **в аккаунте банка**, про корешки
  ничего не знает и отдаёт заявки (`ТипДокумента = IncomingBankApplication`) как есть, по возрастанию
  `@Документ`; курсор — `@Документ` последней строки страницы.

Это расхождение с первоначальной идеей Артемьева (05.08): «прогнать ВНР на двух аккаунтах (альфа и
тбанк) на каждом из стендов». Так корешки пришлось бы писать в чужой аккаунт, поэтому направление
развернули — ВНР идёт в аккаунте Тензора, а в банк уходит межаккаунтное чтение. Номера аккаунтов
банков, которые дал Галимов 06.08, при таком направлении не нужны.

> [!key-insight] ClientID аккаунта Тензора = 3
> Со слов [[Тимошенко А.А.|Тимошенко]] (11.09), в коде это не проверялось. Он же идёт в файлы
> `<стенд>_cloud_clients` архива ВНР.

## Контракт метода

Вход: `ProgramId` (`@ВидЦены`), `Partner` (`ClientId` — аккаунт банка в облаке, `ContractorId` — `@Лицо`),
`DryRun`. Выход — запись со счётчиками `RequestsFound`, `StubsCreated`, `SkippedDuplicates`,
`SkippedUnknownState`, `Errors` и выборкой `Stubs` (`DocId`, `OperationId`, `RequestNumber`, `LinkType`)
для сверки из консоли. Идемпотентность — по `OperationId` = `ИдентификаторДокумента` заявки; вставка
пачками по 500, каждая в своей `CreateTransaction(READ_COMMITTED, WRITE)`.

Состояние заявки (`ДокументРасширение.СостояниеКраткое`) → `ТипСвязи` корешка: «Создана»,
«Отправлена», «Ошибка отправки», «Одобрена», «На подключении» → `REQUEST_IN_PROGRESS`; «Успешно
обработана», «Подключен договор» → `REQUEST_SUCCESS`; «Отклонена», «Истекла», «Отозвана» →
`REQUEST_FAILURE`. «Удалена» (-1) корешком не оформляется. Дату смены состояния банк не хранит,
поэтому `EffectiveDate` = дата создания заявки для любого статуса.

## Скрипт ВНР

`developer_script.py` + `DeveloperScript.orx` в `www/service/Модули/LoyaltyReferral/`. Логики в нём
нет: берёт банки-партнёров программ SabyBank и на каждого зовёт метод, складывая счётчики; ошибка по
одному партнёру не роняет остальных; итог — `LogMsg` построчно и `LogRedis` сводкой. Если программ
SabyBank в аккаунте нет — строка в лог и выход.

**Партнёры берутся запросом к БД, а не через `ReferralProgram.GetPartners`.** Три причины: скрипту не
нужна проверка прав на публичный метод; не нужен поход в сервис бизнес-групп ради списка, который есть
в `ВидЦены` + `ВидЦеныВидКарты` + `Карта`; и главное — `GetPartners` отсекает партнёров с расторгнутым
агентским договором, а для исторических заявок такого партнёра пропускать нельзя. `ClientId` банка
лежит в `Карта.Атрибуты -> ReferralProgram ->> PartnerId`; если он пуст, читать заявки негде — партнёр
считается ошибкой и логируется.

Архив (`s_timoshenkoaa_<номерВНР>_v1.zip`, 7-Zip): `DeveloperScript.orx`, `developer_script.py` и
`fix/test/rc/prod_cloud_clients` с одним `3` внутри. Для `pre-test` в регламенте описан только
`pre-test_billing_clients` (номер аккаунта биллинга, не ClientID облака) — файла нет, там скрипт
отработает вхолостую на всех клиентах.

## Версии: где метод есть и где он рабочий

Метод влит в `rc-26.4220` и разошёлся по 4225/4227/4232/4234/4239/5100. Но контракт `GetBankRequests`
чинили отдельно — ошибка на стенде 03.09 («Нельзя вызвать из другого аккаунта, требуется Service
Contract»), фикс `4e4e4d7b56`: `returns` `RECORDSET` → `TABLE` и `module_api_part="1"`.

| Ветка | Состояние |
|---|---|
| `rc-26.4220`, `rc-26.4225` | метод есть, контракт **старый** — межаккаунтный вызов не пройдёт |
| `rc-26.4227`, `rc-26.4232`, `rc-26.4234`, `rc-26.5100` | метод есть, контракт исправлен |
| `rc-26.6100` | `create_stubs_for_existing_requests.py` и `GetBankRequests` **отсутствуют** |

Отсюда два следствия. Прогонять ВНР можно только на стенде с версией от 4227. И до выхода 6100 метод
надо туда доложить — иначе он потеряется вместе с задачей,
причём проверять надо файлом, а не `git branch --contains`.
