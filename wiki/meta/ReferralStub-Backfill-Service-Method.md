# CreateStubsForExistingLeads - миграция корешков как служебный метод вместо ВНР

Navigation: [[SabyBank-RKO-Referral]] | [[Migration-Console-First-Testing-Pattern]] | [[Wasaby-Scripts]]

Поручение №06155143 («Создать корешки для старых заявок по реферальным программам сделок», срок 12.12.26,
критерий в плане октября: «Созданы корешки для старых заявок РП сделок»). Ссылка:
https://online.sbis.ru/opendoc.html?guid=019eca83-7093-7110-b9ef-8a6772a3223d&client=3

Ядро миграции - служебный БЛ-метод по одной реферальной программе, ВНР - тонкий перебор программ.
Для заявок РКО (SabyBank) есть отдельная пара метод + ВНР: [[RKO-Existing-Requests-Stub-Backfill]].

## Что делает ВНР

`developer_script.py` из архива (локальная копия в `LoyaltyReferral/` уже затёрта следующей ВНР
№10064568 - архив брать из документа ВНР):

1. В каждом аккаунте выбирает стандартные программы: `ВидЦены` с `Тип = 37` (`REFERRAL_LEAD`), не черновик,
   не папка (`Раздел@ IS NULL`), `ProgramType <> 1` (не SabyBank), с заполненным `AdObject`. Отключённые
   программы тоже берёт.
2. Нет программ - выходит молча (файлов `*_cloud_clients` в архиве нет, скрипт идёт по всем клиентам).
3. По каждой программе зовёт `CreateStubsForExistingLeads(program_id, False)`; ошибка по одной программе
   не роняет остальные, считается в `Errors`.
4. Итог - `LogMsg` по каждой программе и `LogRedis` сводкой по клиенту: `Программ`, `LeadsFound`,
   `StubsCreated`, `DuplicatesRemoved`, `SkippedDuplicates`, `SkippedNoCard`, `Errors`.

## Что делает метод

Файл `www/service/Модули/LoyaltyReferral/loyaltyreferral/referralprogram/referralprogram/create_stubs_for_existing_leads.py`
(472 строки в `rc-26.5100`). Вход `ProgramId`, `DryRun`. Метод служебный, только роль `PF-Discount`.

1. **Удаляет дубли корешков** программы (`_remove_duplicate_stubs`, стр. 118): по каждому `OperationId`
   оставляет одну строку - с вознаграждением, потом с суммой, потом с продвинутым статусом, потом самую
   раннюю. Дубли могли появиться до исправления гонки создания (`9569d27ee2`).
2. Читает все сделки программы из CRM постранично по 100 (`SourcesSales.GetRawDocs`, фильтр
   `AgentGroupId`, `ReferralProgramId`, `PlaceId = AdObject`, период с 2000-01-01).
3. Пропускает сделки, у которых корешок уже есть (`OperationId` = `ИдентификаторДокумента` сделки),
   и сделки, источник которых не сопоставлен с картой участника.
4. Остальным вставляет корешок в `ВидЦеныДокумент` пачками по 500, каждая пачка в своей транзакции.

Поля нового корешка:

| Поле | Откуда |
|---|---|
| `ТипСвязи` | `Переход.Результат` сделки: true - успех, false - отказ, иначе в работе |
| `ДатаВремя` (CreatedAt) | `Дата` сделки (или `ДатаФазы`). Для старых сделок так и оставили, в живом пути с №09097007 ставится текущее время |
| `EffectiveDate` | `ДатаФазы` сделки для любого статуса |
| `Бонусы` | из старых строк начислений по `Документ` сделки |
| `Сумма` (LeadSum) | `ДокументРасширение.Сумма` из `GetRawDocs` |
| `Атрибуты` | номер, описание, фаза, клиент, ИНН/КПП из `GetRawDocs`, контакт из `GetLeadInfoV2` (вызов на каждую сделку) |

## Идемпотентность

Повторный запуск новых корешков не создаёт: всё уже созданное уйдёт в `SkippedDuplicates`. Прерванный прогон
можно запустить снова - вставленные пачки отсеются. Дубли, если появятся, повторный прогон удалит.

## Замечания к прогону (не блокеры)

- **Гонка с живым путём.** `CreateStub` создаёт корешок под advisory-блокировкой и с проверкой
  существования, а миграция блокировку не берёт и при вставке не перепроверяет: список существующих
  `OperationId` читается в начале, а вставка идёт после обхода сделок с вызовом `GetLeadInfoV2` на каждую.
  Если за это время по старой сделке сработает обработчик смены состояния или источника и создаст корешок,
  будет дубль. Окно небольшое, лечится повторным запуском ВНР (он удаляет дубли). Если хочется закрыть
  совсем - `WHERE NOT EXISTS` по `OperationId` в `_SQL_INSERT_STUBS`, но это доброска в 5100 до прогона.
- **Сумма у старых живых корешков.** Корешки, созданные живым путём до 06.08 (`b4c20ad288`), остались
  без `Сумма`, если сделка с тех пор не меняла состояние. Миграция их пропускает и сумму не проставит.
  В формулировку поручения это не входит; если нужно - отдельная доработка метода (обновить `Сумма`
  у существующих корешков с `NULL`).
- **Реквизиты клиента.** Живой путь после `53dd135c1e` берёт название клиента из `GetLeadInfoV2.Name`,
  а ИНН/КПП из `Контрагент` по `DealFace`. Миграция берёт `КлиентНазвание`/`ИНН`/`КПП` прямо из
  `GetRawDocs`. Есть ли эти поля в ответе `GetRawDocs`, на стенде не проверялось - проверить у QA, что
  у мигрированных корешков видны клиент и ИНН.
- **Объём.** По одному вызову `GetLeadInfoV2` на сделку. Сколько сделок у стандартных программ на бою -
  неизвестно, время прогона не оценено.
- **Месяцы в детализации оффера.** После миграции у стандартных программ появятся старые корешки - та же
  картина, что в ошибке №0918668 по РКО (месяцы в фильтре не с первой заявки). Её разбирают отдельно.

## Проверка на fix (2026-10-21)

По словам Земцовой, ВНР обработала больше сотни записей, у всех заявок есть корешки с клиентом и вознаграждением.
Оставшиеся расхождения со старой статистикой идут от удалённых заявок и вручную сменённого источника, не от ВНР.
Решили пропускать на бой. Подробности: [[zvonok-zemtsova-timoshenko-2026-10-21]].

## Решения и почему

- Миграция - служебный метод по одной программе, ВНР - тонкий перебор программ (метод можно отлаживать из консоли).
- В итогах не писать версию: метод разошёлся по rc от 26.4227 до 26.6200, ВНР шла после 5100; какую назвать - решает пользователь.
- Логин и пароль тестового аккаунта QA в итоги не вставлять.
