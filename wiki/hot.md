## 2026-07-28 — Баг №06244326: фикс реализован и замерен, 14 530 → 225 мс

Продолжение разбора ниже. Правка в `bonus/get_sale_list.py`: CTE `BlockBound` (граница блока отдельно, чтобы не пересканировать `UnfilteredRecords` четырежды) + `BlockSales` / `BlockWarehouseDocs` с `DISTINCT` и `OFFSET 0`; `EXISTS` теперь коррелирует с продажами блока, а не со всем `UnfilteredRecords`.

**Ключевое решение: `OFFSET 0`, а не `AS MATERIALIZED`.** Стенд на **PostgreSQL 10.21** (`SELECT version()` на `test-osr-db19/load-ext-4`), а `MATERIALIZED` — это PG 12+, то есть синтаксическая ошибка. Признак старой версии читался прямо в исходном плане: одноразовые `SuspectSaleIds`/`SuspectWarehouseDocs` показаны как `CTE Scan`, тогда как PG 12+ их бы заинлайнил. `OFFSET 0` работает как барьер на обеих версиях — правка переживёт апгрейд стенда.

**Замер** (те же аргументы: блок 20 000, курсор `2025-09-30 23:59:01+03`, `PeriodStart=-infinity`): Execution 14 530 → **225 мс** (~53×), buffers 2 417 802 → 70 342, спил хеша на диск (`Batches: 16`) исчез. Узел `SuspectSaleIds`: Hash Join → **Nested Loop Semi Join**, 13 287 → **118 мс**, `Index Cond: "Sale" = bs."Sale"` по `iВидЦеныДокумент-Retail`, 11 210 итераций. Тесты — 41 OK, включая `test_8`. Планы и запросы: `logs/explain-06244326/` в репозитории (`logs/` исключён через `.git/info/exclude`).

**Чего замер НЕ доказывает**: прямое сравнение множеств `Suspect*` до/после вырождено — оба пусты. На аккаунте нет ни одной продажи с бонусными движениями более чем на одну `EffectiveDate` (последние бонусные движения — 30.09.2025), непустой случай из живых данных не строится. Эквивалентность держится на логике преобразования (предикат зависит только от `Sale`/`Документ` → `DISTINCT` выносится до фильтра) и на `test_8`; **симметричного теста для розничной ветки нет**. Не закоммичено, ветка не выбрана (rc-26.3248 или rc-26.4100).

**Инструментальное**: `psycopg2`/`psycopg` в окружении нет, `pip install` не проходит (SSL-инспекция ломает цепочку сертификатов PyPI). Рабочий путь к БД — датасурсы PyCharm через `mcp__pycharm__execute_sql_query`; параметр `schemaName` на `search_path` не влияет (имена квалифицировать явно), вывод режется до 10 строк — полный план тянется постранично через `fetch_query_result(offset=…)`.

## 2026-07-27 — Баг №06244326: Bonus.GetSaleList 17 с — hash semi-join в `SuspectSaleIds`

**[[Bonus-GetSaleList-SuspectSaleIds-Hash-Regression]]**: реестр «Бонусы/Покупки» на `лояльность_автотест` (test-online) рисует только первые 30 записей — БЛ отвечает 16–17 с, список рвёт запросы по `iterativeLoadTimeout` (10 с). `EXPLAIN (ANALYZE, BUFFERS)`: **13 287 из 13 325 мс — в CTE `SuspectSaleIds`, который возвращает rows=0**. Планировщик разворачивает коррелированный `EXISTS` в hash semi-join и строит хеш не по ~2.5 тыс. продаж блока, а по всей истории бонусов клиента: 7 бонусных `ВидЦены` × 428 779 строк = 3 001 450, 2.42 млн buffers (536 тыс. с диска), `HashAggregate` → 2 991 883 distinct, хеш на диск (`Batches: 16 (originally 1)`). Промашка оценки в 900 раз (`rows=475` vs 428 779).

**Отвергнуто три версии** (важно, чтобы не ходить по кругу): (1) размер блока / EMA — `_MAX_BLOCK` действительно упёрт в 20 000 при `IterativeRatioEMA` 666.67, но выборка блока стоит **32.8 мс**, EMA ни при чём; (2) отсутствие индексов — все есть и выбираются, полный набор по `ВидЦеныДокумент` лежит в `PriceFormation.Online.dicx:762-1179`, а НЕ в `PricingRetailOnline.dicx` (там объявление неполное); (3) «доработка только в 4100» — `Suspect*` с `rc-26.3211`, на бою `rc-26.3248` текст CTE побайтово тот же.

**Ключевое для приоритета**: стоимость масштабируется по числу бонусных движений **конкретного клиента** (фильтр по его 7 `ВидЦены` из 400), а не по объёму `ВидЦеныДокумент` вообще → на бою это не отсутствует, а не выстрелило. `SuspectWarehouseDocs` быстрый только из-за отсутствия складских бонусов на аккаунте — форма запроса та же. Опровергнут раздел «Индексы — проверено безопасно» страницы [[Bonus-GetSaleList-Duplicate-W-Records-Iterative-Block-Bug]]: проверять надо форму плана, а не наличие индекса. **Фикс не реализован**: `BlockSales AS MATERIALIZED (DISTINCT Sale из блока)` + `EXISTS` по `Retail (Sale, ДатаВремя)`, то же для складской ветки поверх `Warehouse (Документ, ДатаВремя)`; ожидание — доли секунды вместо 17 с.
