# Промокоды: при изменении срока одного выпуска сворачиваются остальные

Ошибка на стенде №100213225 ([ссылка](https://online.sbis.ru/opendoc.html?guid=01a0fd2c-1961-7b92-8d23-2e92b5adeed1&client=3)), автор Куимова Н.В., 02.10.26. Марков А.В. 30.10.26 переназначил на Тимошенко. Веха 26.6100, срок 28.11.26. Стенд pre-test-online, сборка online-inside 26.5100 (1507).

## Симптом

В карточке индивидуального промокода (инд 280924) на вкладке «Выдача» развернуто несколько выпусков. После «Настроить → изменить срок действия → подтвердить» у одного выпуска остальные развернутые выпуски сворачиваются, а шевроны на них показывают состояние, противоположное фактическому.

## Что в логах (sbislogz 02.10.26, 18:11)

- До сохранения отдельными запросами `IndividualPromoCodeEmission.GetList` раскрыты три выпуска: `Folder` = 10379, 10354, 10353.
- `IndividualPromoCodeEmission.Update` по выпуску 10435: `ExpirationPeriod` 50 → 10, ответ `result: "10435"`, ошибок нет.
- Сразу после сохранения один `GetList`: `Folder: [null, "10435"]`, навигация из двух элементов — 30 верхних выпусков плюс один промокод выпуска 10435. Раскрытых 10379, 10354, 10353 в запросе нет.

То есть после сохранения клиент перестроил иерархию вокруг отредактированного выпуска. Он оказался раскрытым, хотя пользователь его не раскрывал — отсюда и «значки показывают противоположное».

## Причина — фронтенд

`client/LoyaltyOnline/PromoCode/Form/_individualIssue/Registry.tsx`, `openEditDialog`: если результат — `EMISSION_UPDATED` и способ выпуска не `MANUALLY`, вызывается `registrySlice.reloadItem(key, { hierarchyReload: true, method: 'query' })` (строки 231–236, автор av.markov, 30.03.2026). `hierarchyReload` перестраивает иерархию заново и ранее раскрытые узлы не сохраняет. Ветка `MANUALLY` делает `registrySlice.reload()`.

## Бэкенд ни при чём

- `IndividualPromoCodeEmission.GetList` отдает выпуски и промокоды корректно: `Id` = `10435` и `10435-670749`, `Folder` — родитель, `Folder@: true` только у выпусков.
- `IndividualPromoCodeEmission.Update` возвращает id выпуска; после сохранения список отдается с новым сроком (10 дней).
- Серверное событие `online.loyalty-system.individual-promo-code-emission.generated:<id>`, на которое подписан реестр (`onRequestUpdate` → тот же `hierarchyReload`), публикуется только в `generate.py:201`; `update.py` его не шлет. Второй путь сброса раскрытия в этом сценарии не участвует.

## Вывод

Корневая причина в `client/` — вне зоны backend-разработчика. Задачу стоит перевести на фронтенд (автор правки — Марков А.В.). Направления фикса: перезагрузка без `hierarchyReload` либо обновление данных строки без перестройки иерархии.

## Открытые вопросы

- Как платформой перезагрузить один узел, не теряя раскрытие остальных (`reloadItem` без `hierarchyReload`, возможности `listHeavy`-фабрики).
