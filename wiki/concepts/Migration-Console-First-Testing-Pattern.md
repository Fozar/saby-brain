# Console-First Migration Testing Pattern

Navigation: [[SabyBank-RKO-Referral]] | [[zvonok-musohranov-timoshenko-2026-07-22]]

Методология проверки **сложной, необратимой миграции данных** (не «select+update»), сформулированная [[Мусохранов-Андрей-Владиславович|Мусохрановым]] на примере перевода существующих реферальных сделок на корешки (`ВидЦеныДокумент`). Суть: **отладить ядро миграции как отдельный метод из консоли до того, как оборачивать его в ВНР и передавать QA**.

---

## Когда применять

Признаки, что миграция требует этого подхода (а не обычной доброски):

- Результат нельзя выразить как один `SELECT` + один `UPDATE` — есть ветвления, вызовы чужих сервисов, побочные записи.
- Миграция создаёт записи, количество которых должно точно совпасть с ожидаемым (риск «накрутить» лишние `ВидЦены`: 10 записей на сделку вместо 2).
- В цепочке есть **непредсказуемый внешний вызов** (напр., метод ЦРМ «может вернуть чёрт знает что»).
- Проверить результат можно только в БД, а объём (сотни сделок × десятки программ) исключает сплошную ручную сверку.

## Порядок (метод → консоль → ВНР → QA)

1. **Выдели ядро как вызываемый метод** (напр., по одной реферальной программе), а не только как тело ВНР.
2. **Построй контролируемую фикстуру** с известным ожиданием: реф. программа с 3 сделками — 2 с бонусными начислениями, 1 без (не успех) → ожидается ровно 2 корешка.
3. **Прогони метод из-под консоли**, сверь по идентификаторам и количеству: было N записей → должно добавиться M → проверь, что добавилось ровно M нужных.
4. **Итеративно лови и чини ошибки на месте**: докинул фикс в метод → перезапустил → открыл таблицу → проверил. Цикл дешёвый.
5. Только **после** отладки метода — оберни его в ВНР для прогона по всем офферам.
6. **Передавай QA с явным сценарием**: не «проверь всё», а что именно и как смотреть (какие таблицы/поля/количества). Выборочная проверка нескольких программ из десятков не доказывает корректность остального.

## Почему не отлаживать сразу через ВНР

> [!key-insight] ВНР — «комбайн»
> Тестирование через ВНР дорого: много согласований, медленный цикл, разработчик и QA «замучаются». Отдельный метод отлаживается быстрее и **надёжнее** — локализация ошибки и фикс происходят в одном шаге. Спихивать проверку сложной миграции целиком на QA — неправильно: у QA нет способа убедиться, что по неотсмотренным сделкам не создан мусор.
