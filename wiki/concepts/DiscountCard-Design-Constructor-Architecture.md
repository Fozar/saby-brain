# DiscountCard Design Constructor — Architecture

Source: `Техническое задание.pdf`, раздел 6 «Техническое решение».

## Термины

- **Конструктор сайтов** — набор сервисов/визуальных компонентов для WYSIWYG-настройки сайтов без программиста. Позволяет создавать многостраничные сайты в аккаунте и просматривать в рантайме.
- **Тип конструктора** — конфигурация конкретного применения: список виджетов для магазина, шаблоны, контекст данных, поддерживаемые расширения адаптива, настраиваемые стили.
- **Сайт** — набор страниц (составных виджетов) с темизацией и навигацией. **Страница** — фрейм с набором виджетов, подгружает только нужные для себя данные/компоненты. **Фрейм** — виджет, собранный из других виджетов в формате JsonML, может быть вложен.

## Решение

Дизайн Дисконтной карты (Дизайн ДК) реализуется как **сайт на конструкторе сайтов** с новым типом конструктора и тремя обязательными страницами:

| Страница | Назначение |
|---|---|
| **AppleWallet (AW)** | Лицевая сторона для iOS |
| **GPay (GP)** | Лицевая сторона для Android |
| **Оборотная сторона** | Общая для обеих платформ |

При отправке образа: Android → страница GP + оборотная сторона; Apple → страница AW + оборотная сторона.

Лицевая сторона состоит из блоков: Логотип, Баннер, Название, Инфоблоки, Штрихкод/QR-код — положения регламентированы публичным API. Результаты хранятся в сервисе **site-builder**.

## Прикладные объекты (ПО)

Загружаются в контекст данных конструктора (режимы конструирования и проигрывания):

- **ПО ДизайнКарты** — настройки блоков страниц AW/GP. Хранится в ПО (а не в свойствах виджетов), т.к. нужна синхронизация данных между двумя разными страницами сайта — единственный способ платформы разделить данные между страницами. Логическая единица предметной области «Дисконтные карты» — может существовать реестр всех настроенных дизайнов, со своим ID и хранением в БД.
- **ПО КартаЛояльности** — данные конкретной выданной карты клиенту; используется для подстановки значений в инфоблоки в режиме проигрывания (например, страница Карты в SabyGet). В режиме конструирования показываются демо-данные.

## Синхронизация между AW и GP

Через ПО ДизайнКарты синхронизируются: логотип, баннер, цвет фона, настройки инфоблоков (клиент/кэшбэк/бонус...), настройки штампиков, штрихкод/QR-код. Редактируются через прикладные редакторы виджетов (не через platform theme mechanism — оформление AW и GP регламентировано разными сторонними API, платформенные темы не подходят).

## Конструктор — упрощённая раскладка

Используется платформенный компонент `SitesEditor/editorConnected:Editor` с **прикладной раскладкой**, а не стандартной (клик по чипсе в стандартной раскладке ставит виджет в произвольное место по курсору — здесь позиции строго регламентированы).

> [!note] DnD только для инфоблоков
> Перемещение через drag-and-drop возможно только в рамках позиций для инфоблоков. Остальные блоки (логотип, баннер, штрихкод) можно только настраивать/скрывать (технически остаются на раскладке), но не перемещать.

## Каталог виджетов

### Страница AppleWallet (корневой виджет — прикладная раскладка)

Свойства оформления зависят от страницы: AW — фон+заголовки+текст; GP — только фон; Оборотная сторона — оформление не редактируется.

| Виджет (`LoyaltyPublic/DiscountCard/Design/constructor:*`) | Перемещение | Скрытие | Данные |
|---|---|---|---|
| `Layout` (корневой) | нет | нет | Логотип/Баннер/Штрихкод/Блок1-5/Название/ДопТекст(GP) — контентные свойства |
| `Logo` | нет | да (место резервируется) | ПО ДизайнКарты.Логотип |
| `Banner` | нет | да | ПО ДизайнКарты.Баннер + Штампики |
| `Barcode` | нет | нет | ПО ДизайнКарты.ТипШтрихкода |
| `InfoBlock` (×5, Блок1-5) | нет | да (скрывается, не выделяется — изменение поведения vs. старого редактора) | ПО ДизайнКарты.Блок1-5, тип БлокДанныхКарты |

**Инфоблок** — механизм подстановок: текст содержит теги `[Имя подстановки]`, заменяемые при отображении данными из ПО КартаЛояльности. Доступные подстановки: `[Баланс бонусов]`, `[Кешбэк]`, `[Скидка]`, `[Имя клиента]`, `[Срок действия]`, `[Посл. посещение]`, `[Покупки]`, `[Посещений]`.

Быстрые действия виджетов: выбор цвета фона/текста/заголовков (`Controls-editors/properties:BackgroundEditor`), выбор картинки логотипа/баннера, настройка штампиков (компоновка, цвета активный/неактивный/подарок, иконки), выбор типа штрихкода (перечисление).

### Страница GPay

Те же типы виджетов, только другая раскладка блоков (нет отдельного цвета заголовков/текста — только фон).

### Страница Оборотной стороны

Корневой виджет — платформенный `LayoutWidgets/stack:ColumnView`. Виджеты: `TextBlock` (заголовок+описание), `Address` (+выбор точки на карте), `Phone`, `Link` (+валидация URL), `ReferralLink` (заголовок + описание с подстановкой ссылки + выбор точки продаж). Оформление здесь не редактируется вовсе.

### Прикладной компонент чипсов

На основе платформенного `ExtControls/ExtendedBlockList`. Логика клика зависит от типа виджета:
- **Инфоблок-чипсы** (Кэшбэк/Баланс бонусов/Клиент/Скидка/Срок действия/Ваш текст) — записывают предустановленные заголовок+описание в первое пустое поле ПО ДизайнКарты.Блок1-5; когда все 5 заняты — чипсы скрываются.
- **Баннер/Логотип/Название** — виджеты всегда на раскладке, но скрыты; чипса делает видимым.
- **Штампики** — открывает прикладной редактор штампиков баннера.

## Внедрение в сценариях (13 экранов)

Общий паттерн: режим **чтения** → платформенный плеер `FrameRouting/Page:PagePlayerConnected`; режим **редактирования** → `SitesEditor/editorConnected:Editor`. Методы создания (`*.Create`) создают сайт Дизайна ДК и инициализируют его значениями по аналогии со старым механизмом (название, оборотная сторона, баннер/логотип с привязанной точки продаж), возвращая `SiteId` на фронт; методы сохранения (`*.Update`) пишут `SiteId` в `CardTemplate.SiteId`.

Экраны: Диалог создания Типа карты · Страница Дизайн · Реестр типов карт · Список дизайнов ДК · Диалог создания Дизайна · Пустое представление реестра ДК · Анкета выдачи ДК · Страница для скриншота баннера со штампиками · Карточка Акции (вкладка «Отображение на карте», для штампованных акций) · Карточка Промокода (вкладка «Дизайн») · SabyGet ×3 (превью карты на странице заведения, выданная карта, страница Карты) · Реестры на Inside ×2 (все типы карт, Витрина/Бонусы) · Карточка Типа карты.

Для превью в реестрах вместо старых методов (`DiscountCardType.GetListSimple`, `DiscountCardType.GetTemplateList`, `DiscountCardDesign.GetList`, `CardType.GetAdminList`) везде переходим на платформенный **`Site.GetList`** с параметром `IncludeSites` — массовое получение скриншотов сайтов.

Новое поле `SiteID` протягивается по цепочке методов Лояльности/SabyGet: `Card.GetListV2` → `Establishment.BonusDetails`; `Card.ReadV2` → `BonusCard.Read`; `CardAdm.Read` → `BonusCard.ReadForAdmin`.

**Не меняется:** редактирование шаблона (по проекту конструктор туда не внедряется).

## Конвертация данных сайта для мобильных устройств (AW/GP)

Т.к. данные хранятся в БД через ПО ДизайнКарты, при отправке образа нужно только вычислить расположение инфоблоков нужной страницы: вычитать сайт по ID → найти корневой виджет `constructor:Layout` → в свойствах block1..block5 найти виджеты `constructor:Block` и посмотреть на поле ПО ДизайнКарты, которое каждый отображает (нумерация блоков — по декомпозиции фрейма, разная для AW/GP/оборотной стороны).

## Миграция дизайна из Брендбука

Реализуется конвертер: читает оформление с сервиса брендбука + настройки сайта конструктора → создаёт новый сайт с типом конструктора Дизайн ДК, наполняя страницы по настройкам брендбука (алгоритм будет описан отдельно перед реализацией). Данные о блоках AW/GP сейчас хранятся **только** в брендбуке; при конвертации сохраняются в `CardTemplate.ViewDetails`. Сформированный сайт сохраняется в site-builder, `SiteId` — в новом поле `CardTemplate.SiteId`.

> [!contradiction] Contradicts [[DiscountCard-Subsystem-Overview]]
> Существующая страница описывает «Брендбук» как текущую интеграцию для «настроек дизайна для карт и промокодов». Этот проект **выводит Брендбук из эксплуатации** для этой роли: «В рамках проекта отказываемся от хранения настроек дизайна на сервисе брендбука, требуется удалить после конвертации данные на сервисе брендбука» (ТЗ, раздел «Конвертация дизайна карты из брендбука»). После завершения миграции (см. [[DiscountCard-Design-Constructor-WorkPlan]], этап «Конвертация дизайна карты из брендбука») интеграция с Брендбуком в этой роли должна считаться устаревшей.

## API

Используемые API не меняются, новые — не требуются (кроме внутреннего хелпера `GetBannerInfo(CardTemplateId) → {BannerImg, StampSettings}` для страницы скриншота баннера со штампиками — раньше эти данные читались из брендбука на предзагрузке).
