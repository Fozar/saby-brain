# Очистка розницы: проверка продаж с лояльностью

Задача в разработку №072010033 ([ссылка](https://online.sbis.ru/opendoc.html?guid=019f804b-0c7c-7fef-8081-bc63e78c89e1&client=3)), автор Зуев Н.П., исполнитель Омельяненко, в плане октября Тимошенко. Описание одной строкой: "Реализовать метод по проверке продаж с лояльностью для очистки розницы согласно ТЗ". Вложений и обсуждения нет. Веха 26.6100 online/inside: 06.10 Тимошенко запросил перенос срока с 10.10 на 28.11 (на согласовании у Зуева).

Проект: "Очистка розничных продаж в схеме клиента" (Зуев, [проект](https://online.sbis.ru/opendoc.html?guid=5f4d4a7b-92e6-4a2b-9f67-9452c87b2637&client=3)). ТЗ лежит во вложениях проекта ("Техническое задание", sabydoc).

## Что говорит ТЗ

Клиент чистит розничные данные (смены, продажи, чеки) старше 2 лет, чтобы не платить за диск. Запуск из Saby Space (СБИС.Диск) -> DWC -> итеративный метод розницы `Retail.Cleaning` (Рахманов, №072010017, пока только фича `rtl_clearing_active` и заглушка `Retail.Access2DBCleanup`). Розница идёт по сменам и перед удалением продаж спрашивает разрешения у связанных сервисов.

Про лояльность (раздел 3, таблица "Особенности очистки"):
- Sale и SaleNomenclature не удаляем, если на продаже есть хоть какая-то лояльность.
- Основной признак: ид продажи есть в `ВидЦеныДокумент`.
- Переделывать реестры и отчёты лояльности под удалённые продажи дороже, чем эффект проекта, поэтому такие продажи просто остаются (в реестрах розницы они будут скрыты).

Контракт (раздел 6.3.2 "Со стороны лояльности"):
- `LoyaltyProgram.HasLoyalty()` -> bool. True, если на аккаунте есть лояльность и её применения, тогда надо звать вторую проверку. False, значит препятствий нет и `CheckClearedSales` можно не звать.
- `LoyaltyProgram.CheckClearedSales(<массив @Sale>)` -> массив @Sale, которые удалять нельзя. Пачки не больше 500.

Соседняя задача №072010040 (Омельяненко): подписаться на события удаления, чтобы чистить данные СДК/сервиса покупок. Омельяненко 05.10 спросил, нужно ли это вообще; Федько: "уточнять у текущих владельцев". К этой задаче не относится.

## Что выяснено в коде

- `ВидЦеныДокумент` для розницы расширяет модуль `PricingRetailOnline` (`PricingRetailOnline.dicx`): поля `Sale` и `ReferralSale` (оба `LINK1-N` на `Sale`, `on_delete=1`). Значит таблицы лояльности и розницы в одной схеме, проверка делается прямым SQL.
- Индексы: `Retail` (`Sale`, `ДатаВремя`) с условием `"Sale" IS NOT NULL`, `ReferralSale` (`ReferralSale`, NULL не индексируются). Обе проверки идут по ним.
- Реферальное начисление пишется без `Sale`, продажа только в `ReferralSale` (см. тест `get_sale_list.py`). Поэтому проверять надо оба поля.
- Позиционная лояльность (`ВидЦеныНоменклатураДокумента.SaleNomenclature`) пишется вместе со строкой на продажу, отдельно не проверяем.
- Методы `LoyaltyProgram.*` для облака лежат в `PriceFormation.Online/LoyaltyPrograms.orx`, код в `priceformationonline/loyaltyprograms/loyaltyprogram/`. Очистка только облачная, офлайн не нужен.

## Тех. решение

- `HasLoyalty`: `EXISTS` по `ВидЦеныДокумент` с `"Sale" IS NOT NULL` или `"ReferralSale" IS NOT NULL`. То есть "есть хотя бы одна продажа с лояльностью", а не "настроена программа": настроенная, но ни разу не применённая программа удалению не мешает.
- `CheckClearedSales(Sales INT4[])`: `UNION` двух выборок по `Sale = ANY` и `ReferralSale = ANY`, на выходе `array_agg`. Пусто или None -> `[]`. Больше 500 -> `sbis.Error`.
- Обе: `access_mode="0"`, `module_api_part="1"`, без фичи (новые методы, никто не зовёт).
- Строгий вариант по ТЗ: любая строка в `ВидЦеныДокумент` блокирует удаление продажи, тип программы не важен.

## Открытые вопросы

1. **Сертификаты** (Зуев, Усов). Продажа и оплата сертификата тоже пишутся в `ВидЦеныДокумент` (`Атрибуты->'Cert'`). По строгому правилу такие продажи не удалятся никогда, а задача Усова №072010051 ждёт, что сертификат удалится после удаления всех его продаж. Надо ли исключать строки с `Cert` из проверки?
2. **Не "лояльность" в ВЦД** (Зуев/Федько). В таблицу пишутся и наценки (`PERCENT_MARKUP`, `MANUAL_MARKUP`), ручное снижение цены, строки с `Применена = false`. Блокировать продажу из-за них или только из-за скидок/бонусов/карт/промокодов?
3. **Имя параметра** `Sales` (Рахманов). ТЗ говорит "единственный аргумент массив чисел", имени нет. Если зовут позиционно, разницы нет.
4. **Каскад `on_delete=1`**. Похоже на каскадное удаление строк ВЦД вместе с продажей. Если это так, то без нашей проверки удаление продажи стёрло бы бонусные операции и изменило бы баланс. Проверить на стенде одним запросом к `pg_constraint`.
