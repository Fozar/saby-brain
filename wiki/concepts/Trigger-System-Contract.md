# Trigger System Contract (Система триггеров)

Платформенный механизм Saby, формализующий контракт между прикладными областями (Лояльность, Розница, CRM, Трекинг) и инфраструктурой маршрутов через **json-описания событий и действий**, хранимые в отдельном репозитории `triggers-data`. Введён проектом [[CustomerJourney-Scenarios-Project]] как фундамент для [[Route-Platform-Architecture]]. Источник: [[customer-journey-tz-2026-07-03]].

## Роль триггеров — сугубо техническая

Триггеры **не настраиваются пользователем напрямую**. Они создаются автоматически при настройке каждого нового маршрута и при срабатывании просто уведомляют проходчик о новых изменениях (проходчик сам решает, как переместить клиентов по этапам). Для запуска **действий** (не имеющих события-активатора) также создаются тех.триггеры — их «поджигает» проходчик принудительно.

## Понятийная модель

| Термин | Определение |
|---|---|
| Событие | Что-либо, определяемое прикладной областью (напр. «совершена покупка») |
| Действие | Реакция на событие, задающаяся в Триггере |
| Объект | Определяет множество триггерных Событий и множество возможных на них Действий |

## Настройка события — 3 шага

1. Добавить описание события в виде JSON в репозиторий триггеров
2. Внедрить отправку события в прикладном сценарии
3. Добавить недостающие объекты в репозиторий либо выбрать из существующих в реестре триггеров

## Настройка действий

Формируется JSON-файл в директории `base/actions` репозитория триггеров. Прикладная область может добавлять свои уникальные действия, допустимые только к своему объекту.

Чтобы заработал список действий:
1. Добавить описание действия в JSON в репозиторий триггеров
2. Реализовать БЛ-метод действия в прикладной области — принимает единственный аргумент `Record` с полезной нагрузкой, описанной в объекте
3. Зафиксировать доступность действия на объектах конфигурации

Планируется доработка от команды триггеров: описание требуемых полей ввода для действий вплоть до конкретных компонентов-лукапов (для полей, значений которых нет в контексте).

## Обработка ошибок и отладка

При ошибке в БЛ-обработчике триггерного действия проходчику маршрутов передаётся факт неудачного выполнения → ошибки этапа-действия отображаются в **карточке прохода**. Системные ошибки ищутся классическими средствами (облачные логи, профилирование) — выполнение триггерного действия сводится к простому вызову метода БЛ.

## Интеграция компонента триггеров (`layout.Card`)

Точка встраивания в прикладной интерфейс (пример на Wasaby, допускается React-вариант):

```jsx
<Triggers.layout.Card
  options="{{options}}"
  context="{{context}}"
  saveCard()
  removeCard()
  onSaveCallback()
  onChangeCallback()
  onRemoveCallback()
/>
```

- `options.payload` — перечень полей условий/подстановок в действиях; для документа рекомендуется оставить payload документа и поджигать через `Notify` с event
  - `options.payload.NAME` — можно объявить `required: true`
  - формат поля: либо формат триггеров (`CustomType`, `DisplayTitle`, `Type: "atEMPLOYEE"` и т.д.), либо формат дата-контекста (`Id`, `Version`, `Title`, `NodeType`, `Parent`, …)
- `options.actions.exclude` — действия, которые нужно исключить
- `options.actions.NAME` — правила для конкретного действия (`required`, `readonly`)
- `context.object` — объект (тип документа), куда подключается `layout.Card` — endpoint карт данных + выборка в БД
- `context.event` — событие, по которому выполняется перечень условий/действий; вызов через `Trigger.Notify`; если событие не передано, но нужно выполнить конфигурацию в момент времени — `Trigger.Notify` с ID конфигурации из `onSaveCallback()`
- `context.phases`, `context.regulations` — доп. инфо для построения перечня действий/полей/подстановок
- `context.id` — передаётся прикладному разработчику при сохранении
- `context.callback` — метод, который триггеры вызывают по факту выполнения всех действий; получает 2 параметра: (1) payload триггера, (2) статус обработки действий

Для триггеров, встроенных через `layout.Card` по месту, фиксируется отдельный тип — **обособленные (произвольная конфигурация)**.

### Набор действий по умолчанию для "обособленных" (аналог `CustomDocTemplate.json`, не зависит от типа документа)

`SocNetAggregation.Send`+`Notification.Send.Detached` (отправить), `Object.Create` (создать), `Object.AddComment` (комментарий), `History.Write` (запись в историю), `Code.Execute` (выполнить код), `Http.Request` (http-запрос), `Document.Mark` (пометка), `Calendar.Create` (событие в календарь).

При передаче в `_options.mount` название действия загружается как **обязательное, неудаляемое** действие со своим набором mount-параметров.
