# Удаление и скрытие клиента: свои обработчики событий для дисконтных карт

Задача в разработку №03179884 ([ссылка](https://online.sbis.ru/opendoc.html?guid=1b6ce09e-ef5b-4a0d-8f0b-da3ad2ca7865&client=3)), автор Лукьянов Н.Л. (Клиенты), заведена 17.03.2026. Веха 26.6100, срок 28.11.2026. На выполнении у Тимошенко с 12.10.2026, подтверждено лентой задачи. Критерий приёмки: «Реализовано согласно задаче».

**Запрос.** Сейчас CRM сама проверяет наши карты и сама зовёт наш `DiscountCard.OnDestroyClient` при удалении и скрытии клиента. Лукьянов просит забрать эту логику к нам и подписаться на события контрагентов самим.

## Как сейчас (CRM, `crm/core`, ветка rc-26.6100)

Модуль «Активные продажи», `on_event.py` строки 102-123:

| Событие | Обработчик CRM | Что делает для карт |
|---|---|---|
| `online.contractor.deleting.allow` | `CRMClients.AllowDeletePhysic` (`activesales/crmclients/helpers.py:32`) | Для `Type = 2` и заполненного `Entrepreneur` запрос `HAS_SALE_OR_DOCS_OR_EMPLOYEE` (`templates.py`). Наш кусок (если загружен `PriceFormation.Online`): есть ли в `ВидЦеныДокумент` по картам клиента операции без `Sale`, без `Документ`, с `ДатаВремя` не NULL и меньше infinity |
| `online.contractor.deleting.deleted` | `CRMClients.DeleteClientHandlerForRec` (`handlers.py:37`) | `DiscountCard.OnDestroyClient([Entrepreneur])`, тип не проверяет |
| `online.contractor.deleting.deleted` | `CRMClients.DeletePhysic` (`editor.py:142`) | Удаляет `ЧастноеЛицо`, если `Тип = 4` |
| `contractor.hide` | `CRMClients.DeleteClientHandler` (`editor.py:116`) | По `@Лицо` контрагента берёт `Entrepreneur` для `Type = 2` и зовёт `OnDestroyClient` |

## Контракты событий (публикует `contragents/online`)

- `online.contractor.deleting.allow`: `LocalPublishRecord`, в обработчик идёт запись контрагента (`@Лицо`, `Entrepreneur`, `Type` enum, `UUID`, `Название`, `НеОтображается` и др., см. `delete.py::_prepare_delete`). Ответ: Record с полем `Allowed` (bool). Удаляют, только если все вернули True или None (`permissibility.py::can_delete`), иначе контрагента скрывают.
- `online.contractor.deleting.deleted`: та же запись, публикуется после `Contractor.DeleteInBaseSql` (`delete.py:362`). Для ИП и КФХ (`Type` 1, 3) до события уже вызван `PrivateFace.Delete`.
- `contractor.hide`: только `@Лицо` контрагента (int). Публикуется из удаления, когда удалять нельзя (`delete.py:769`), и из ручного скрытия в реестре (`set_display.py:157`).
- `Type`: 0 организация, 1 ИП, 2 физ. лицо, 3 КФХ, 4 гос. инспекция, 5 группа компаний (`contragents/common`, `ContractorKind`).

## Что у нас

- `DiscountCard.OnDestroyClient` (`priceformationonline/discountcard/discountcard/on_destroy_client.py`): берёт карты с `Карта.Лицо` = частное лицо клиента. У настоящих карт (тип CARD, ECARD) ставит `Заблокировано = True` и `Лицо = NULL` через `RetailDiscountCard.Update` (уходит уведомление в сервис ДК). У служебных персональных карт (без эмиссии) сохраняет ид. клиента в `Атрибуты.Client.ClientId`.
- `Карта.Лицо` ссылается на `Лицо` с `on_delete = 2` (по всей видимости обнуление ссылки). Для обычных карт там частное лицо (`Контрагент.Entrepreneur`), для партнёрских промокодов там `@Лицо` контрагента (`has_partner_activity.py`).
- Подписки модуля: `PriceFormation.Online/on_event.py`, `event.SetLocalCallback` в `OnEndAllLoadModules`. Приоритета у подписок нет, от CRM модуль не зависит (`PriceFormation.Online.s3mod`).

## Тех. решение

Три новых метода в `DiscountCard.orx` (category Handle, trusted_only) и подписки в `on_event.py`. Код в `discountcard/discountcard/handle_client_delete.py`:

1. `DiscountCard.HandleClientDeletingAllow(Contractor) -> Record{Allowed}`: тот же запрос по операциям, что был у CRM. Только для `Type = 2` с заполненным `Entrepreneur`, иначе True. Права на удаление клиента по-прежнему проверяет CRM.
2. `DiscountCard.HandleClientDeleted(Contractor)`: `on_destroy_client([Entrepreneur])`, как у CRM, без проверки типа.
3. `DiscountCard.HandleClientHide(ContractorId)`: `Entrepreneur` из `Контрагент` по `@Лицо` и `Type = 2`, затем `on_destroy_client`.

Совместимость: пока CRM не убрала свои вызовы, всё выполнится дважды. Это безопасно (кроме порядка, см. вопрос 1): проверка просто дублируется, а второй `OnDestroyClient` уже не найдёт настоящих карт (у них `Лицо = NULL`), служебным картам повторно запишет тот же ид. Порядок выката: сначала мы, потом CRM убирает свой кусок запроса и оба вызова `OnDestroyClient`. Сам `OnDestroyClient` оставляем, пока его зовёт CRM.

## Что выяснено по коду

Проверено 26.10 по CRM `origin/rc-26.6100`, контрагентам `rc-26.6100` и нашей заготовке.

**Как идёт удаление в контрагентах** (`delete/delete.py`, `permissibility.py`):
- Сначала запись скрывается, затем `can_delete`: обработчики `allow` плюс наличие событий. Дальше либо удаление, либо событие `contractor.hide`. Обработка может быть асинхронной.
- `deleted` несёт сохранённую запись контрагента (с `Entrepreneur`) и публикуется уже после удаления контрагента.
- У ИП и КФХ `PrivateFace.Delete` вызывается в самих контрагентах до `deleted`. Поэтому перестановка подписок в CRM этот случай не закрывает.

**CRM:**
- `DeletePhysic` удаляет частное лицо только у контрагента `Type = 2` и только если тип частного лица равен 4. Это значения разных перечислений, не путать.
- `DeleteClientHandlerForRec` сейчас зовёт `OnDestroyClient` до `DeletePhysic`. После переноса подписки в наш модуль порядок между модулями ничем не гарантирован.
- Остальные проверки продаж, документов и сотрудников CRM оставляет себе.

**Наш `allow`:** смотрит не на наличие карты, а на операции `ВидЦеныДокумент` через `Карта.Лицо`: без `Sale` и `Документ`, с конечной непустой `ДатаВремя`. Карты менять в нём нельзя, это только проверка.

**`OnDestroyClient`:**
- Обычные карты (CARD, ECARD) блокирует и обнуляет `Лицо`, через `Update` уведомляет discount-cards.
- Персональные служебные счета без эмиссии не блокирует, только сохраняет `ClientId` в атрибутах.
- При скрытии вызывается тот же метод, отвязка остаётся. Событие `contractor.recover` публикуется, наших подписок на него нет, владельца карте никто не возвращает.

**Не проверено на стенде.** Повторное удаление скрытого клиента с уже отвязанной обычной картой, скорее всего, не увидит её операции через `Карта.Лицо`, и `allow` разрешит удаление. Это вывод по коду. Девять тестов вызывают обработчики напрямую, порядок событий целиком не проверяют.

## Решения и почему

- В заготовке поведение CRM перенесено один в один, включая отвязку при скрытии. Так проще принять и выкатить: сначала мы, потом CRM убирает своё.
- `allow` не используем для изменения карт: он только проверяет, и после него удаление может не произойти.
- Для встречи предлагаем гарантировать обработку карт до удаления частного лица. Два способа: CRM удаляет частное лицо отдельным последним шагом после всех обработчиков `deleted`, либо контрагенты публикуют событие до удаления. Выбор за встречей.

## Открытые вопросы (для встречи 26.10)

1. **Порядок с `CRMClients.DeletePhysic`** (Лукьянову). Наш обработчик `deleted` ищет карты по `Карта.Лицо`. Если частное лицо удалится раньше, ссылка обнулится, карты останутся незаблокированными и без владельца. Сейчас это везение. Нужна гарантия: финальный шаг после обработчиков или событие до удаления частного лица.
2. **Скрытие и восстановление** (Лукьянову, Омельяненко). Сейчас при скрытии карта и блокируется, и отвязывается, хотя клиента могут восстановить; в коде CRM на это TODO. Либо оставляем как есть, либо при скрытии только блокируем, а отвязываем при удалении, и решаем, что делать при восстановлении. Второй вариант меняет поведение.
3. **ИП/КФХ.** Частное лицо удаляется в контрагентах до `deleted`: как гарантировать порядок и для них.
4. **Повторное удаление скрытого клиента** с отвязанной картой (см. выше): нужно ли это закрывать.
5. **Выкат.** Подтвердить порядок: наши подписки раньше, чем CRM уберёт свой кусок запроса и вызовы `OnDestroyClient`. Полный сценарий проверить интеграционно, юнит-тестов на порядок событий недостаточно.
6. **Вне задачи.** Партнёрские промокоды (`Карта.Лицо` = контрагент) и франшиза (карты ищутся только в своём аккаунте) не обрабатываются ни сейчас, ни в заготовке.
