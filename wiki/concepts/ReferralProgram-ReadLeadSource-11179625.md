# Источник сделки для реферальной программы: чтение из CRM вместо hstore

## Задача

Ошибка на стенде №11179625 (автор Феклистов А.Д., 17.11.2026): обработчик реферальной программы при смене источника на сделке читает источник из `ДокументРасширение.Параметры` — значение устаревает после смены источника.
Задача MR №11185257, MR GitLab !154716 (и !154717-!154721, !154769 — та же ветка в разные ветки вех).
Ветка `26.6100/bugfix/ad.feklistov/read_lead_source_by_advert` → rc-26.6100, коммиты c4f27f01, 3d85e15d, ddfef8e2.
Сеть MR: price-formation !154716-!154721, !154769; crm/core !302643-!302650; crm/advert-service !85581-!85586.

## Где остановились

20.11.2026 — ревью проведено, в GitLab не писали (по просьбе Тимошенко). MR открыт, часть замечаний бота не закрыта, автор ответил на два.

## Что выяснено по коду

- `ReferralProgram.HandleLeadStateChanged` подписан на локальное событие `Lead.StateChanged` (`LoyaltyReferralOnline/on_event.py`) — событие приходит по всем сделкам аккаунта, не только по реферальным.
- Было: `_extract_referral_code` разбирала `ДокументРасширение.Параметры` через `hstore_to_dict` и брала `place`.
- Стало: `sbis.EndPoint('crm-service').SalesSources.ReadSourceOnObjectService(ObjectId=@Документ, TypeName='Лид')`, из ответа берётся `Place` → `get_referral_code_by_ad_object(int(place))`. Проверка поддерживаемого состояния перенесена выше вызова, чтобы не дёргать сервис на нерелевантных состояниях.
- Семантика `Place` совпадает с `AdObject` реферального кода: то же сравнение в `ReferralProgram.GetLead` (`PlaceId` против `AdObject`) и в `handle_source_changed` (`Place` из события `salessources.source_changed`).
- Метод `SalesSources.ReadSourceOnObjectService` появляется в crm/advert-service в ветке `26.6100/bugfix/ad.feklistov/read_source_on_obj_wo_rights`: `read_source_on_object_service` — то же чтение, но без проверки прав пользователя (в отличие от `ReadSourceOnObject`, где есть `check_access(AccessFlag.READ)`). В rc-26.6100 метода ещё нет.
- `handle_exceptions` (`priceformationcommon/helpers/wrappers.py`) ловит исключение и пишет в лог только строку «Ошибка при выполнении функции <модуль>.<функция>» — без текста ошибки и без id сделки.
- В crm-service этот же вызов делает `_merge_lead.py`: таймаут 1500 мс константой `_TIMEOUT_MS`, вызов обёрнут в try/except с `WarningMsg` и с текстом исключения, ответ проверяется на пустоту.

## Замечания ревью (в порядке важности)

Автор MR — внешняя команда (CRM/маркетинг): в цепочке MR есть crm/core и crm/advert-service.
Поэтому придирки по коду их части не пишем (у них свои конвенции: `SetTimeout` вместо `timeout=` в конструкторе, своё именование), замечания только по существу поведения и контракта.


1. Нет try/except вокруг вызова crm-service. Сбой или таймаут → исключение проглатывает `handle_exceptions`, корешок не переводится, вознаграждение не начисляется, в логе нет ни причины, ни id сделки.
2. Нет проверки ответа на None: `source.Get('Place')` без `if source`. Guard `if source else None` был в промежуточном коммите 3d85e15d и убран в финальном ddfef8e2.
3. Порядок выкатки: price-formation !154716+ зависит от advert-service !85581+, где появляется метод. Без обновлённого crm-service вызов падает «метод не найден» и обработчик перестаёт работать целиком (и молча, см. п. 1).
4. Изменилось поведение при смене источника на нереферальный: раньше корешок прежнего партнёра закрывался по устаревшим параметрам, теперь источник нереферальный → `_extract_referral_code` вернёт None → корешок останется «В работе» навсегда. `handle_source_changed` этот случай тоже не закрывает (там просто выход). Нужно решение: закрывать корешок или считать нормой.
5. Путь удаления сделки (`_fail_stub_of_deleted_lead`) теперь тоже зависит от чтения источника. Если связь с источником при удалении снимается, корешок не переведётся в «Отрицательно завершена» — регрессия к задаче [[ReferralStub-Status-On-Lead-Deleted-10232436]]. Проверить на стенде.
6. Нагрузка: синхронный RPC на каждое изменение состояния сделки аккаунта и на каждое удаление. Раньше внешних вызовов в обработчике не было.
7. `hstore_to_dict` в `core/referral_program.py` осталась без использования (`import re` нужен только ей).

## Открытые вопросы

- Что должно происходить с корешком, когда источник сделки сменили на нереферальный (п. 4)?
- Есть ли способ узнать источник сделки без RPC (например, форматом чтения самой сделки)?
- Подтвердить на стенде, что при удалении сделки источник ещё читается (п. 5).

## Идея без RPC (предложение внешней команде)

Событие `Lead.StateChanged` уже несёт `Документ.ДокументРасширение.Параметры`, где лежит `place` — но он устаревает после смены источника. Если CRM начнёт класть в событие актуальный источник (или обновлять параметры при смене источника), price-formation сможет читать источник из события, и синхронный вызов crm-service из обработчика не понадобится: исчезнут и лишняя нагрузка, и риск тихого отказа.
