# PromoCode.GetList - поиск по коду выданного промокода

Задача в разработку №03129162 ([ссылка](https://online.sbis.ru/opendoc.html?guid=dc9d476f-7d58-4b90-831f-6a0b6cf82d86&client=3)), автор Морозов А.В., заведена 12.03.2026 по обращению клиента. Веха 26.6100, срок 28.11.2026. Исполнителем числится Омельяненко (с 29.04). 05.10 Тимошенко попросил переназначить задачу на себя, 06.10 переспросил ("Тут тоже ждем?"). На 07.10 задача так и висит на Омельяненко, других сообщений и решений по ТД в задаче нет.

**Запрос.** У клиента тысячи кодов. Администратор или оператор КЦ вводит код в поиск реестра промокодов, чтобы проверить, действует ли он, и ничего не находит. На видео из задачи (Presto: Скидки и акции, Промокоды) код ищут вручную: открывают папки "Сертификаты 500/1000..." и листают коды внутри промокода "1000 - Самурай".

## Как было

Реестр строит `PromoCode.GetList` (`priceformationonline/loyaltyprograms/promocode/get_list.py`, класс `PromoCodeListWithCursor`). Фронт передаёт строку в `SearchString`, а бэкенд сравнивал её только с `ВидКарты.Название`: `ILIKE`, совпадение по словам и полнотекстовый поиск. Код выданного промокода (`Карта.Номер`) не участвовал. Фронт менять не нужно: строка поиска уже уходит в `SearchString`.

## Где лежит код и как поднять его до промокода

- Общий, партнёрский и промокод за активность: `Карта.Эмиссия` указывает прямо на промокод (`ВидКарты`).
- Индивидуальный: код лежит в **дочерней эмиссии**, это `ВидКарты` того же `Тип = 6` с `Раздел@ = FALSE`, а `Раздел` указывает на промокод (`individual_promo_code_emission/create.py`, `_create_individual_promo_code_emission`). Эмиссия всегда одного уровня.
- В реестре эмиссий нет: условие `"Раздел@" IS NULL` пропускает только промокоды, папки (`Тип = 9`) идут с `Раздел@ = TRUE`.
- Подъём от кода к промокоду уже был в `emissionitem/core.py::_sql_find_by_number` и `promocode/core/triggers.py`: `CASE WHEN E."Раздел@" IS FALSE THEN E."Раздел" ELSE E."@ВидКарты" END`.

Индексы `Карта` в `PriceFormation.Online.dicx` (около строки 1953): `CaseInsensitiveUniqueNumber` по `(upper("Номер"), ТипКарты)` с условием `"Номер" IS NOT NULL` и `ReverseUpperNumber` по `REVERSE(UPPER("Номер"))` (`varchar_pattern_ops`). Полное совпадение идёт по первому индексу (первая колонка `upper("Номер")`, условие индекса покрыто `C."Номер" IS NOT NULL` в запросе). Поиск по любой части кода индексом не покрыт. В той же таблице лежат и все дисконтные карты.

Готовый `find_by_number` не подходит: он отбрасывает неактивные промокоды (`CT."Используется" = 1`) и заблокированные коды, а здесь их нужно находить.

## Договорённости (05.10, решение исполнителя)

1. Совпадение по коду полное, без учёта регистра. Поиск по окончанию или части кода не делаем.
2. Находим и заблокированные и использованные коды, и неактивные промокоды. Черновики (`$Черновик`) не учитываем. Фильтр `IsActive` по-прежнему скрывает неактивный промокод целиком.
3. Совпадения по названию и по коду идут в одну выдачу, без пометки "найден по коду". Фронт не трогаем.
4. Франшиза: у участника в базе может не быть кодов франчайзера, тогда промокод по коду не найдётся. В облако за кодом пока не ходим.
5. Вкладка "Партнёрские" (отдельный реестр, `getPartnerSource`) вне задачи.

## Тех. решение (реализовано в заготовке 07.10)

- `_prepare_filters`: строку `SearchString` без пробелов по краям кладём в служебный фильтр `_SearchCode` (пустая строка -> `None`), в `_default_filters` добавлен `'_SearchCode': None`. Формат кода не проверяем: равенство по индексу дешёвое, а старые коды могли создаваться по другим правилам.
- В запрос первым CTE добавлен `"FoundByCode"`: `Карта C` JOIN `ВидКарты E` по `Эмиссия`, условия `C."Номер" IS NOT NULL`, `UPPER(C."Номер") = UPPER(_SearchCode)`, `C."$Черновик" IS NULL`, `E."Тип" = ANY(CardTypeList)`. Последнее отсекает номера дисконтных карт и учитывает фильтр по типу промокода (`Type`/`TypeList`). Через `CASE` выше получаем `Id` промокода.
- В условие поиска добавлена ветка `OR "ВидКарты"."@ВидКарты" IN (SELECT "Id" FROM "FoundByCode")`. Фильтр по папке, мультинавигация и подтягивание родительских папок (`_add_system_records`) работают как при поиске по названию. Поиск по названию не тронут.
- В `LoyaltyPrograms.orx` у `SearchString` метода `PromoCode.GetList` описание: поиск по названию промокода или по коду выданного промокода (код - полное совпадение без учета регистра).
- pylint по `get_list.py` 10/10. Тесты написаны, не прогонялись (общий тестовый проект).

### Тесты

В `tests/tests_priceformationonline/loyaltyprograms/promocode/get_list.py`, класс `GetList`, 10 новых тестов:

- код общего промокода в другом регистре и с пробелами по краям находит промокод;
- код из дочерней эмиссии индивидуального находит промокод, а не эмиссию;
- промокод в папке находится по коду из корня вместе с папкой;
- часть кода и строка длиннее кода ничего не находят;
- заблокированный код находит промокод;
- код неактивного промокода находит его без фильтра, а с `IsActive=True` нет;
- код-черновик ничего не находит;
- номер дисконтной карты ничего не находит;
- фильтр `Type` действует и на поиск по коду;
- совпадения по названию и по коду приходят в одной выдаче.

Модели: `tests_helpers.model.discount.promocode` (`CommonPromoCode`, `IndividualPromoCodeEmission`, `IndividualPromoCode`), `tests_helpers.model.discount.card.Card`.

## Замечания

- Реестр по умолчанию открывается с `IsActive = true` (`IS_ACTIVE_DEFAULT` в `Loyalty/Core/Promo/Registry/loadUtils`). Значит код неактивного или просроченного промокода по умолчанию не найдётся, пока пользователь не переключит фильтр на все. Это совпадает с поведением поиска по названию и с договорённостью 2, но для сценария "проверить, действует ли код" стоит упомянуть в описании для QA и в help.
- В задаче поле "Изменения в документации: help" - после реализации нужно описание для help (поиск по коду, только полное совпадение).

Первая концептуальная версия для задачи вышла "слишком абстрактной".
