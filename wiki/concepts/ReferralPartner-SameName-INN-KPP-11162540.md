## Что выяснено по коду
- GetPartnerList: _get_partner_id_to_name отбирает приглашённых участников по подстроке Контрагент.Название до SQL. Поэтому добавить поиск по ИНН только в SQL недостаточно: участник уже будет исключён.
- SQL списка партнёров возвращает PartnerId и Name, но не ИНН/КПП. Имя берётся из атрибутов карты, для участников без кода дозаполняется из списка группы.
- GetStubList возвращает ContractorId и ContractorName через Карта.Лицо и Лицо.Название, без реквизитов партнёра.
- Owner/Deals/_partnerSelector/Stack использует GetPartnerList и SearchString; фильтр по партнёру действительно связан с этим методом.
- _deals/Columns.tsx показывает ContractorName без отдельной подсказки с реквизитами.
- Существуют оба пути списка: GetStubList и старый GetLeadList. Старый метод проксирует SourcesSales.GetRawDocs из CRM и обогащает вознаграждением. Нельзя считать правку только GetStubList достаточной для старого режима.
- Inn/Kpp в ReadStub относятся к клиенту заявки, не к партнёру. Использовать их для подсказки партнёра нельзя.

## Решения и почему
Согласован только бэкенд обоих пунктов. По имени поиск по подстроке, по ИНН/КПП — полное совпадение. Отбор до пагинации. Дополнительный SQL при непустом поиске ограничен уже отобранными приглашёнными участниками; отклонившие приглашение и посторонние контрагенты не добавляются. Реквизиты возвращаются через LEFT JOIN Контрагент, пустые строки приводятся к null. Названия и идентификаторы не меняются, КПП не обязателен.
В родительском поручении разовая выгрузка уже выполнена Мусохрановым на бою 16.11: опубликовано соответствие шести UUID рефкодов двум контрагентам. Соков должен связать результат со сделками. Это отдельный обход проблемы, не исправление интерфейса.
