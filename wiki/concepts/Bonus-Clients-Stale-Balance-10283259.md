## Где остановились
Найден обратный запрос LoyaltyCard.RequestNotification, обновляющий наш кэш; фактическое исполнение для 5366 не подтверждено. Дальше нужна проверка боевой БД/задач СДК; в PyCharm такого подключения нет. Передача Юре как доказанно чужой ошибки пока преждевременна.

10.11.2026: доступ предоставлен. Через PyCharm выполнены два SELECT в u215-11 на osr-u215-db2-1.unix.tensor.ru:5432, с явной квалификацией таблиц схемой _011d50c3. Данные не меняли, пересчёт не вызывали. Кэш персонального счёта действительно устарел; причина, почему не сработало его обновление, ещё не установлена. Далее проверить путь обработки NextChangeDatetime и обновления кэша после сгорания.

### Проверка пути обновления 10.11.2026
Дополнительный SELECT qr_581cf321: NextBonusExpiration на 5366 равен 19.10.2026, на 5365 пуст; срок карты не ограничен; SQL-сессия UTC. Первая попытка дополнительного SELECT отклонена из-за отсутствующего столбца IsBonus, после удаления этого поля запрос выполнен; данных не изменяли.

Проверенные исходники: run_expiration_trigger.py выбирает персональные счета по NextBonusExpiration, но передаёт агрегаты CustomerId/BonusId/ExpireIn/ExpireSum в триггер уведомлений, не выполняя пересчёт кэша. update_bonus_balance_cache.py пересчитывает явно переданные CardIdList и отдельно обновляет NextBonusExpiration. Само наступление NextChangeDatetime в этих методах не запускает пересчёт. notify.py:171–187 передаёт NextChangeDatetime с балансом, а notify.py:32–66 отправляет данные через Card.HandleChangeData. Поэтому отсутствие планового обновления во всей системе не доказано: получатель события и возможный обратный запрос требуют отдельной проверки. _get_bonus_data при from_cache=False может обновить кэш, диагностические вызовы этого пути на бою не выполняли.

Установленная причина неверного значения в реестре: чтение просроченного кэша без проверки срока. Почему кэш не обновился после 19.10 — пока неизвестно; сбой фоновой задачи не доказан. Сравнение исследователем с доступным origin/rc-26.5118 не выявило отличий в трёх файлах этого пути, но точный состав боевой сборки 26.5118-135 не подтверждён. Не связывать с Wallet без проверки получателя.

### Уточнение контракта обновления после сгорания
10.11.2026: пользователь разрешил читать СДК для внутреннего анализа, но запретил ссылаться на его реализацию при передаче ошибки. Внутренняя цепочка прослежена: NextChangeDatetime сохраняется как будущее изменение; плановый запрос свежих данных возвращается в price-formation через LoyaltyCard.RequestNotification с CardIdList. Наш handle.py:393–399 вызывает get_card_data(from_cache=False), а notify.py:269–293 пересчитывает баланс с update_cache=True. Персональные счета из плановой цепочки не исключены. Поэтому прежняя неопределённость о наличии обратного запроса снята: такой путь предусмотрен. Это не доказательство его фактического исполнения для счёта 5366.

Для передачи допустимы ссылки только на собственный контракт и наблюдаемые результаты. Нужны фактические сведения об отправке Card.HandleChangeData и исполнении LoyaltyCard.RequestNotification по нужному аккаунту/CardId=5366. В клиентской БД подтверждён устаревший кэш, но сторона сбоя пока не доказана. Октябрьские облачные логи вне трёхдневного срока хранения. Физическое хранилище DWC в клиентской БД не установлено, SQL для него не придумывали.

Для следующей проверки нужна запись карты и будущего изменения в боевой БД СДК либо подтверждение выполнения задач от Юры. В PyCharm доступны только тестовые/дев/фикс/пре подключения discount-cards; боевого подключения нет. Не подменять online CardId=5366 локальным @Card СДК, а ClientId=11613 — ID аккаунта. Код и данные не меняли.

## Что выяснено по коду
В клиентском логе Bonus.GetClientListWithStats возвращает 1020 для ClientId 11613, CardId 5366; карточка клиента на изображении показывает 0. Начислено 2000, списано 980; 1020 соответствует остатку до сгорания.
В get_client_list_with_stats.py SQL берёт AvailableBonusBalance из Карта.Атрибуты.Bonus без проверки NextChangeDatetime. Собственный баланс не пересчитывается; отдельно запрашивается франшизная часть.
get_bonus_info_for_client.py по умолчанию рассчитывает актуальный баланс, но UpdateCache=False. Это объясняет возможное расхождение карточки и реестра; фактический запрос карточки в приложенном логе отсутствует.
Обновление кэша предусмотрено в change_handler.py через Action.UPDATE_BONUS_BALANCE. Причина отсутствия обновления после сгорания на конкретной карте не установлена.
Серверный лог запроса 866dfdc3-589d-b9a3-df9e-eddc641315a0 содержит только начало, конец и SQL статистики продаж: состояния кэша нет.
Регрессионные тесты реестра есть в tests/tests_priceformationonline/loyaltyprograms/bonus/get_client_list_with_stats.py.

## Решения и почему
Подтверждено поведение кода: реестр использует сохранённый баланс без проверки актуальности. Причина расхождения у Алины ещё не доказана. Не объявлять установленной причиной сбой фонового обработчика или ошибку СДК без данных.
Предварительное направление: учитывать актуальность кэша и пересчитывать устаревшие остатки перед выдачей. Окончательный способ ещё не выбран.
