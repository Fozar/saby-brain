# Плеер Дизайна ДК на странице картинки баннера и на странице получения карты

Две связанные задачи проекта [[DiscountCard-Design-Constructor-Project]]. Обе завёл Михель 23.09, веха 26.6100 (срок 28.11.2026), UI делает Ютман, БЛ Тимошенко. Критерий в плане: "Задача выполнена согласно требованиям".

- №09236765 [Реализовать страницу для формирования картинки баннера со штампиками, на новом дизайне карт](https://online.sbis.ru/opendoc.html?guid=01a0cdca-3c38-72ac-baec-9d2ba2745ba7&client=3). Этап 8 проекта. UI: плеер с виджетом баннера и штампиков, ИД ПО карты и дизайна в адресе страницы. БЛ: добавить эти ИД в адрес страницы, с которой снимается картинка. Переписки в задаче нет.
- №09236874 [Внедрить плеер нового дизайна на страницу получения дисконтной карты](https://online.sbis.ru/opendoc.html?guid=01a0cdcf-8d2f-7abd-a804-cd504d3eb896&client=3). Этап "Внедрение конструктора в сценариях отображения". БЛ: добавить в адрес страницы ИД сайта, ПО дизайна и ПО карты. В задаче вопрос Михеля: в адресе сейчас зашифрованный ИД карты, можно ли кормить его обработчику ПО.

## Что было в ТЗ и что поменялось

ТЗ (раздел "Страница для скриншота баннера со штампиками") предлагало другое: плеер на эту страницу **не** внедрять, оставить старый компонент баннера, а данные (картинка баннера и настройки штампиков) брать новым методом `GetBannerInfo(CardTemplateId)`. Задача №09236765 от этого отказывается: на странице будет плеер, а он сам читает ПО ДизайнКарты по ИД. Поэтому `GetBannerInfo` не нужен, нужен только правильный адрес страницы.

Для страницы получения карты ТЗ ничего не говорит. Ближайший образец: анкета выдачи (задача №06242857). Там `Questionary.CreateCard` в СДК уже отдаёт `SiteId`, `LoyaltyCardDesignId` (`@CardTemplate`, только если есть сайт) и `CardId` (`@Card` СДК), см. `dcservice/sabyget/questionary/create_card.py:142-161`.

## Задача №09236765: адрес страницы картинки баннера

**Адрес собирается не в price-formation, а в СДК discount-cards.** `get_banner_image_screen` в `www/DCService/dcservice/online/cardtype/update_stamps_banner_image.py:108-161`:

```
{host}page/card-design-banner?stampsCount=..&stampsToGift=..&themeId=<ApplicationKey брендбука>&isSnapshot=true
```

Скриншот делает `webshot.ImageConverter.PrivateConvertUrlToDisk` под сессией аккаунта (`AuthByClientID`), элемент `pfcDesign-Banner`. Картинка кешируется в `CardType.Info.StampsBannerImage` по типу карты и **числу штампиков**, а не по карте.

Кто зовёт:
- `CardType.UpdateStampsBannerImage` (генерация по всем картам типа или обновление кеша). Конкретной карты здесь нет: число штампиков берётся из карт или из ключей кеша.
- `handle_change_data.py:512-555` (пустой прогресс) и `:559-620` (изменилось число штампиков у карты). Здесь карта есть.

Сама страница `card-design-banner` лежит в price-formation (`client/LoyaltyOnline/ui/DiscountCard/BannerImage.pagex`), её предзагрузка (`DiscountCardType/BannerImage/Config.ts`) читает настройку брендбука по `themeId`.

**Почему на новых дизайнах картинки сейчас не будет вообще**, даже если поменять адрес:
- `_get_stamps_banner_image` выходит с "Дизайн карты не на брендбуке. Сформировать изображение невозможно." (`update_stamps_banner_image.py:194`), если у шаблона нет `ApplicationKey`;
- `with_stamps` у шаблона считается только из `ThemeData` брендбука (`dccore/cardtemplate/entity.py:234`), а `_update_empty_stamps_banner_img` без него ничего не делает;
- в price-formation перегенерацию запускает `discountcardtemplate/save.py:165-198` только при `ThemeData`; для конструктора это место в `LoyaltyCardDesign.Write` СДК, там TODO "Обновление образов, штампиков" (`write.py:63`).

### Тех. решение (СДК)

В `get_banner_image_screen` развилка по шаблону: если у активного шаблона есть `SiteId`, адрес строится от ИД ПО, иначе как сейчас (брендбук).

```
{host}page/card-design-banner?loyaltyCardDesignId=<@CardTemplate>&stampsCount=..&stampsToGift=..&isSnapshot=true
```

плюс `cardId=<@Card>`, если фронту он нужен и карта есть. Шлюзы `ApplicationKey` и `with_stamps` для дизайнов на конструкторе заменить на "есть `SiteId`" и "заполнен `Stamps` в ПО" (решение Лебедевой из [[Promotion-CardView-Constructor-Stamps]]). В price-formation правок не видно.

Варианты, что передавать для числа штампиков:

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. ИД дизайна + `stampsCount`/`stampsToGift` в адресе | работает и для генерации по типу карты, где карты нет; кеш по числу штампиков не ломается | ПО КартаЛояльности на странице не используется, фронт должен взять счётчик из адреса |
| Б. ИД дизайна + ИД карты (как в задаче) | плеер берёт всё из двух ПО | для `UpdateStampsBannerImage` карты нет; картинка с прогрессом одной карты кешируется для всех карт с тем же числом штампиков, при отличиях карты будет неверно |

Склоняюсь к А (`cardId` можно передавать, когда карта есть, но не опираться на него).

### Реализация (12-13.10)

```
{host}page/card-design-banner-new?designId=<@CardTemplate>&stampsCount=..&stampsToGift=..&isSnapshot=true
```

Сделано в СДК discount-cards, в price-formation правок нет:

Для брендбука, как раньше, по `ThemeData`.

## Задача №09236874: адрес страницы получения карты

Страница: `sabyget/.../get-discount-card/<id>` (роутер SabyGet переводит на `sg-get-discount-card`). Фронт (`LoyaltyPublic/DiscountCard/ReceivingPage/PrefetchConfig.ts`) берёт `<id>` из пути и зовёт в СДК `Questionary.GetCardData(Identifier)`, картинку карты (`Questionary.GetCardImage`) снимает со страницы `design-preview`. Расшифровка `<id>`: `get_card_key` (`dcservice/sabyget/questionary/helpers.py:95`) понимает и UUID карты, и зашифрованный `"<client_id>_<card_id>"`.

**Ссылку в BL собирает price-formation:** `CreateECardImpl._get_link` в `priceformationonline/discountcard/discountcard/create_ext.py:200-208` (`DiscountCard.CreateExt`, диалог выдачи карты), затем короткая ссылка `/go/...`.

**Вопрос Михеля про зашифрованный ИД уже неактуален.** 01.10 Кузаков (`1a86602f39`, ошибка №052710346, только `rc-26.6100`) перевёл ссылку на UUID карты: шифрованный ключ с `//` терялся при переходах, и страница падала. Теперь в адресе `Карта.Идентификатор`, по нему СДК находит карту.

**Обсуждение в задаче (05-06.10), решения нет:**
- Курников: формулировка в задаче не нравится; что будет, если для карты передать в адресе другой дизайн и зачем это нужно.
- Омельяненко: в ссылке достаточно UUID карты, остальное получим по нему.
- Ютман: можно, но нужен метод БЛ, который отдаст ИД карты и ИД шаблона.
- Курников: ИД карты по порядку, перебором можно получить все карты; аккаунта на странице нет, а ИД аккаунта отдавать на интерфейс нельзя.
- Ютман: ИД карты нужен как ключ ПО КартаЛояльности для плеера; можно перейти на UUID карты в ПО, тогда ИД отдавать не надо. ИД сквозные, из СДК, с онлайном не совпадают.

Из кода, что важно для решения:
- `NumberCard.Read` (ПО карты, СДК) читает по `@Card` без проверки аккаунта, то есть опасение Курникова по перебору верное.
- `LoyaltyCardDesign.Read` требует аккаунт в сессии и сверяет его с владельцем шаблона (`appobjectimpl/loyaltycarddesign/read.py:68-70`). На анонимной странице SabyGet плеер ПО дизайна так не прочитает (на стенде не проверено).

### Варианты

| Вариант | Что делаем | Плюсы | Минусы |
|---|---|---|---|
| 1. Как в задаче | в адрес `siteId`, `loyaltyCardDesignId`, `cardId` | фронту проще всего | перебор карт по `@Card`; адрес можно подменить (вопрос Курникова); в price-formation нет `@Card` и `SiteId` из СДК, нужен лишний вызов СДК при выдаче; старые ссылки останутся без параметров |
| 2. В адресе только UUID карты, данные из `Questionary.GetCardData` | СДК `GetCardData` отдаёт `SiteId`, `LoyaltyCardDesignId`, `CardId` как `CreateCard` | ссылка не меняется (уже UUID), старые ссылки работают, повтор решения анкеты | `@Card` всё равно уходит на интерфейс, Курников против |
| 3. Только UUID карты, ПО карты по UUID | `GetCardData` отдаёт `SiteId` и ИД дизайна; ПО КартаЛояльности (`NumberCard.Read`) принимает UUID карты | ничего перебираемого наружу не уходит | правка ПО в СДК и фронта; чтение ПО дизайна без аккаунта всё равно надо решить |

Склоняюсь к 3, запасной 2. В обоих в price-formation (`create_ext.py`) ничего не меняется, правка в СДК. Вариант 1 нужен только если Курников его примет.

### Решение и реализация (09-12.10)

09.10 Тимошенко предложил в задаче вариант 3, 12.10 Ютман внесла его в текст задачи как ТР: в ссылке только UUID карты; `Questionary.GetCardData` дополнительно отдаёт ИД сайта и ИД дизайна (`@CardTemplate`), так же как `CreateCard`; ПО КартаЛояльности читаем по UUID карты, `@Card` на страницу не отдаём. Вся доработка в СДК, адрес страницы не меняется.

Где объявлено ПО: `NumberCard` (наследник `LoyaltyCard`) и резолвер `NumberCard.Read` (`Id type="integer"`, `other_service="discount-cards"`) лежат в price-formation, `PriceFormation.Online/DiscountCard.aorx`. Реализация в СДК `dcservice/appobjectimpl/numbercard/read.py` (Кузаков, 01.10) читает карту по `@Card`. Тип `uuid` у `Id` резолвера в других сервисах встречается (Диск, Совещания, HR).

Уточнения 12.10 (решил Тимошенко): ключ ПО только UUID; `GetCardData` отдаёт ещё и `CardId` = UUID карты, потому что в старых ссылках с зашифрованным ключом UUID в адресе нет; чтение ПО без входа на анонимной странице в задачу не входит, проверить на стенде.

**Стоп на совместимости.** `NumberCard.Read` и его резолвер в `.aorx` уже есть в `rc-26.5100`, а 26.5100 вышла в бой 10.10. Смена типа `Id` integer -> uuid несовместима. Фронт анкеты (`QuestionaryConstructor/_cardPreview/View.tsx`) в 26.5100 тоже читает `CardId`, но СДК 26.5100 в `CreateCard` не отдаёт ни `CardId`, ни `SiteId`, так что плеер там до чтения ПО не доходит. `CreateCard.CardId` есть только в `rc-26.6100`, его перевод на UUID безопасен.

Предложен совместимый вариант: `NumberCard.Read` принимает и `@Card`, и UUID (разбирает значение), в `.aorx` тип `Id` резолвера меняется на `string`. Перебор по `@Card` остаётся, но наружу `@Card` больше не отдаём. 12.10 вопрос задан Кузакову: можно ли менять тип параметра у резолвера ПО, который уже в бою. Ответа нет, работа на паузе.

Сделано в worktree `D:/dev/wt09236874` (ветка `26.6100/feature/aatimoshenko/09236874` от `origin/rc-26.6100`), не закоммичено, тесты не прогнаны:
- `SabyGet.orx`: в `GetCardData` новые возвраты `SiteId`, `LoyaltyCardDesignId`, `CardId` (UUID); в `CreateCard` тип `CardId` стал UUID;
- `create_card.py`: `CardId` = `sdk_card.Get('Identifier')` вместо `@Card`;
- `get_card_data.py`: шаблон из `card_type.active_template` через `SQL_GET_TEMPLATE`, `LoyaltyCardDesignId` только при заполненном `SiteId`, `CardId` = `card.identifier`.

Не начато: `NumberCard.Read`, `AppObjectImpl.orx`, `.aorx` в price-formation, тесты (`tests_dcservice/appobjectimpl/numbercard/read.py`, `tests_dcservice/sabyget/questionary/get_card_data.py`, `create_card.py`). После правки Ютман надо поменять тип `CardId: number | null` в `Questionary/Helpers.ts` и загрузчик ПО плеера.
