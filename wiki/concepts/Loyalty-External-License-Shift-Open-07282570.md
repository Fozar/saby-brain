# Лицензия внешних систем при открытии смены

Ноябрьский план №606980697, пункт `635460072`. Срок пункта: **2026-11-29**; срок карточки: **2026-11-29**. Плановая оценка: 1.7 ч (как возвращено СБИС, не переоценивалась).

## Где остановились

**Новое ТР на согласовании.** По [[zvonok-matyushev-timoshenko-license-dispatcher-2026-11-19|звонку с Матюшевым]] конкретный параметр лицензии выбирает действие, `LicenseDispatcher` и `BillingHelper` выполняют вызовы. Это заменяет предыдущий эскиз с `if ACCOUNT_COMPONENT_ID`. Конкретные сигнатуры ниже — предлагаемая реализация, а не утверждённый контракт. Код не менялся.

- В `license_parameter.py` добавить `_check_for_consumers(dispatcher, points)`. `BalanceLicenseParameter` делегирует существующей балансной проверке диспетчера; `BasicLicense`, `ProLicense` и `MaxLicense` наследуют это поведение. `IntegrationLicense` получает через диспетчер один флаг на аккаунт и возвращает его для каждой подходящей точки. Сбор точек остаётся в `LicenseConsumersGetter`: один запрос `GetAll`, общие подключения UDS/PB на все ТП, iiko — по сопоставлению.
- В `license_new.py` сохранить интерфейс `check_for_consumers`: пропускать пустой список, вызывать метод параметра, записывать результат в `LicenseConsumers.states`. Балансные методы проверки, ограничений и списания принимают только балансный параметр, иначе `sbis.Error` до биллинга. В `billing_helper.py` оставить небалансный `License.Require` без привязки и чтение булева поля; сбой/некорректный ответ — не `False`.
- В `refresh_license.py` добавить новый параметр под существующей фичей в общий цикл и убрать отдельный `_get_integration_states`. При сбое `GetAll`/`Require` для внешнего типа сохранить только его прежние записи, а обычные лицензии обновить; подтверждённый пустой список удаляет прежние записи. Для балансных типов политика недоступности сохраняется. Формат кеша и общий интервал не меняются; у внешнего статуса нет отдельного интервала повторной проверки.
- В `GetTypesBySalePoint` оставить существующую в локальном диффе попытку обновления в пределах двух секунд для пустого/просроченного снимка. Тесты: один запрос на аккаунт, разметка ТП, отсутствие балансных RPC для `IntegrationLicense`, регрессия Basic/Pro/Max, разница между `False`, сбоем и пустым списком, холодный кеш. На стенде проверить, что предупреждение не блокирует смену. `CheckLicense` без ТП, выбор клиента, регистрация, фронт и отдельный кеш не входят в задачу.

**Звонок 19.11, 13:22:** [[zvonok-matyushev-timoshenko-license-dispatcher-2026-11-19]]. Матюшев предложил, чтобы конкретный параметр лицензии выбирал действие полиморфным вызовом, а обращение к биллингу оставалось в диспетчере и его `BillingHelper`. ТП нужны для показа предупреждения, не для списания. Это направление для пересмотра ТР, а не согласование предыдущего эскиза с `ACCOUNT_COMPONENT_ID`; точный контракт и `CheckLicense` без ТП не согласованы.

Пользователь передал ответ Матюшева на согласовании: «Тут нужно чуть глубже смотреть... Если все сделать правильно на уровне LicenseDispatcher, то все сценарии заведутся без лишних телодвижений». Замечание не означает, что уже согласован конкретный контракт. Код не меняли.

Сверка по коду и обсуждение с оракулом: текущий `check_account_component` вызывается из отдельной ветки `RefreshLicense`; предлагается описать `LOYALTY_INTEGRATION` как отдельный тип параметра и использовать штатную цепочку `LicenseConsumersGetter → LicenseDispatcher.check_for_consumers` без специальной сборки в сценарии. Выбор способа проверки делает диспетчер. Для открытия смены достаточно существующего снимка по точкам; `CheckLicense` читает его по обязательному `SalePointId`, поэтому регистрация без точки не заработает от одного изменения диспетчера. Уточнение к Матюшеву: нужен ли в этой задаче уже готовый `CheckLicense` без ТП или достаточно общей проверки в диспетчере и подключения её в открытии смены. Холодный кеш — отдельный вопрос: без типа лицензии из `GetTypesBySalePoint` касса не вызывает `GetLicenseWarning`; перенос проверки в диспетчер этого сам по себе не меняет.

По просьбе пользователя сузили дифф с 9 до 6 файлов (5 файлов бэкенда и один файл тестов). `cache.py`, `warnings.py` и `GetLicenseWarning` совпадают с релизной веткой. Ожидание пересчёта до двух секунд осталось только в `GetTypesBySalePoint` для устаревшего/пустого кеша. Формат кеша не менялся: при сбое внешней проверки сохраняем её последнее подтверждённое состояние, но публикуем заново пересчитанные балансные лицензии; повтор внешней проверки — по существующему интервалу кеша.

Изолированный регрессионный тест подтвердил, что до изменения сбой `GetAll` не давал обновить балансную лицензию. После упрощения 9/9 с заглушками, pylint SBIS 10/10, `git diff --check` без замечаний. Штатные тесты и интерфейс пока не проверены: сборка всё ещё `266100` вместо `271000`. Правки локальные, без коммита.

Техрешение одобрено. Пользователь переключил основную папку `price-formation` на `rc-27.1100`; правки в ней, без коммита/MR. Фронт и связанные сценарии выбора клиента/регистрации не менялись.

Добавлены пакетный запрос действующих подключений, одна проверка `LOYALTY_INTEGRATION` на аккаунт и использование обновлённого кеша при открытии смены. После ревью оракула общий профиль UDS/PB охватывает и дополнительные ТП, получение типов и предупреждений ожидает пересчёт не более двух секунд на вызов, а сбои RPC сохраняют прежний снимок. В `tests/tests_priceformationonline/licence/loyaltylicence/refresh_license.py` добавлено девять сценариев.

Изолированный прогон с заглушками платформы: до реализации и исправлений по ревью подтвердились падения ожидаемых проверок, после изменений 9/9. Pylint SBIS 10/10 по изменённым Python-файлам. Штатный прогон не запускался: текущая сборка стенда `266100`, для ветки нужен `271000`. Следующий шаг — собрать стенд `online` с нужным SDK, прогнать BL-тесты и вручную проверить, что предупреждение видно и смену в Online/Desktop можно открыть.

**Техрешение по повторному разбору (на согласовании).** Пользователь подтвердил: не задаём Матюшеву вопрос и не выходим за сценарий открытия смены. Не закладываем отдельное обновление уже открытого окна и не переносим проверку намеренно на следующую смену.

- В `billing_helper.py` и `license_new.py` выделяем проверку небалансного компонента на аккаунт. `License.Require` получает `ComponentIDs=['LOYALTY_INTEGRATION']` и `BindLicense=False`; `true`/`false` читаем из отдельного одноимённого поля. Пустой ответ, отсутствующее поле и сетевой сбой — состояние не получено, прежний результат не затирается. Ветки проверки и списания балансных лицензий не меняем.
- В `license_parameter.py` собираем точки одним `IntegrationCfg.GetAll` для `uds`, `pb`, `iiko_card` с `account=sbis.Session.ClientID()` и без приостановленных профилей. Контракт `rc-27.1100` поддерживает массив `names` и по умолчанию исключает паузы. Для UDS/PB используем `contragents`, активное общее подключение распространяется на все ТП; iikoCard — только `salesPointMatching`. Нет ТП — нет запроса лицензии. Не берём `IntegrationSalepointsCache` за источник активных подключений.
- `refresh_license.py` под `ext_loyalty_license` добавляет статус `LOYALTY_INTEGRATION` по полученным точкам в существующий снимок, при успешном пересчёте удаляются устаревшие записи. При недоступности источника остаётся прежний снимок и время его обновления; не записываем ложное отсутствие лицензии.
- В `get_types_by_sale_point.py` при пустом или просроченном кеше под существующей фичей получаем `RefreshLicense` в рамках текущего открытия, с существующими таймаутами и возвратом локального кеша при недоступности облака. Розница иначе не вызовет `GetLicenseWarning`, если первичный ответ не содержит типа лицензии. Формат ответа, фронт, предупреждения и синхронизацию кеша не меняем. Если данных нет даже после попытки, предупреждения об отсутствии не выдумываем, смена должна открываться.
- Проверки: одна проверка аккаунта на несколько ТП, общий и точечный профили, точки без активных подключений, `true` и `false`, отключённая фича, сетевой/неполный ответ, первое открытие на пустом кеше, не блокировать смену при предупреждении в Online/Desktop. Настройки интеграций, частичное обновление при сохранении, регистрация и выбор клиента — вне задачи.

Нет взятия в долг или запрета редактирования настроек. Утверждение ниже о блокировке по скриншоту неверно.
- В `origin/rc-27.1100` `LoyaltyLicense.GetLicenseInfo` — заглушка. Рабочий путь для кассы использует `GetTypesBySalePoint` и `GetLicenseWarning`, который уже умеет читать `LOYALTY_INTEGRATION` из кеша по ТП. Первый метод запускает обновление асинхронно и может прочитать старый/пустой кеш. Код не менялся, сценарий на стенде не прогонялся.

В `ExternalLoyalty.GetActiveExternalLoyalty` общее подключение без списка ТП используется для всех ТП (для iiko общих подключений нет). Кеш заполняется обработчиком при `UPDATED`/`RESUMED` с изменением настроек, так что по одному пустому списку нельзя достоверно определить, что подключение общее и действует сейчас.

Рекомендация оракула: брать действующие подключения пакетно из `IntegrationCfg.GetAll` (запрос на систему, не на точку), сохранять последнее подтверждённое состояние при сбое, не выдавать неизвестность за отсутствие лицензии. Осталось согласовать поведение пустого кеша: предупреждение при следующем открытии или обновление уже в текущем окне после фоновой проверки. Код не меняли.

Ответы из ТЗ (раздел 6.1.4 «Проверка лицзий для внешних систем лояльности»):
- Создаём новый параметр ограничения лицензий LOYALTY_INTEGRATION; проверяем через API биллинга, состояние кешируем в Online.
- При открытии смены: предупреждение об отсутствии лицензии, НЕ блокирует открытие.
- Взятие в долг не делаем. Редактировать настройки подключений при отсутствии лицензии не запрещаем — проверка только в целевых сценариях.
- Частичное обновление кеша предусмотрено при редактировании настроек механик лояльности, в т.ч. внешних бонусных систем.
- Сценарии: настройки интеграции (баннер), открытие смены (GetLicenseInfo), выбор клиента (CheckLicense LOYALTY_INTEGRATION), регистрация в PremiumBonus (CheckLicense без ТП, null).

Контракт с пользователем подтверждён: небалансный параметр проверяется через License.Require({ComponentIDs: ['LOYALTY_INTEGRATION']}), как в фронте external-discount. Задача — только бэкенд.

## Постановка и критерий

Внедрить проверку лицензии внешних систем при открытии смены. Доработать RefreshLicense и LicenseDispatcher для небалансного параметра внешних систем. В карточке отдельно написано: «Со стороны кеша и проверок уже поддержано». Критерий плана: в 27.1100 согласно требованиям.

**Кэш и бэкенд (price-formation):**

LOYALTY_INTEGRATION в этом списке нет — кэш этим типом не наполняется.
- Тип `LOYALTY_INTEGRATION` есть в `LicenseType` (types.py) и в License.orx (CheckLicense/GetLicenseInfo его перечисляют), но состояние в кэш не пишется.

**Контракт небалансного параметра (подтверждён фронтом):**
- `loyalty/external-discount`, `client/ExternalBonus/Connection/_base/Preload/LicenseDataFactory.ts`: проверка через `License.Require(Params: {ComponentIDs: ['LOYALTY_INTEGRATION']})` — без потребителей; в ответе флаг по компоненту и `RestrictionConfig[COMPONENT_ID]`.
- Тот же паттерн массово используется в других репозиториях (edo и др.) — это стандартный вызов биллинга для небалансных компонентов.

**Потребители для кэша:**
- `IntegrationSalepointsCache` (priceformationonline/discount/priceformation/core/integration_salepoints.py, параметр `PriceFormation.IntegrationSalepoints`): ТП подключений по типам интеграций; заполняется в `integration_handler.py` при сохранении подключений UDS/PB/iiko.

## Решения и почему

**Исторический черновик (до повторной сверки; не использовать без перепроверки):**

Фронт открытия смены готов и работает по кэшу. Делаем бэкенд:

1. `license_parameter.py`: признак `IS_BALANCE = True` в базовом классе (у небалансных — False); новый класс `IntegrationLicense` — LICENSE_TYPE=LOYALTY_INTEGRATION, COMPONENT_ID='LOYALTY_INTEGRATION', SUITABLE_REASON_LIST=[] (списания нет); потребители — ТП из IntegrationSalepointsCache (новый метод `LicenseConsumersGetter._list_sp_external_integration()`).
2. `billing_helper.py`: метод `check_unbalanced_license(component_id)` → `sbis.License.Require({ComponentIDs: [component_id]})`, сетевые ошибки → ServiceUnavailableError (как в остальных методах).
3. `license_new.py` (`LicenseDispatcher.check_for_consumers`): для небалансного параметра один вызов Require на аккаунт, состояние размазывается по всем потребителям; балансная ветка без изменений.
4. `refresh_license.py`: `IntegrationLicense` добавлен в `all_license_params` — кэш наполняется LOYALTY_INTEGRATION по ТП интеграций.
5. Тесты: новые кейсы в `license_dispatcher.py` и `refresh_license.py` (состояние в кэше, сбой биллинга).
